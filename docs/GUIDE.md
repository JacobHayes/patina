# Guide

How to run a program under Patina, find bugs in it, and read what Patina found. Every flag
is in `patina COMMAND --help`; this guide shows how they fit together. The examples use the
programs in [examples/](../examples/README.md), run from the repository root.

## Running a program

```sh
patina run --seed 7 -- ./myprog --port 8080
```

Everything after `--` is the program and its arguments. A program given by a path runs from
that path, as given (a relative one made absolute, a symlinked directory kept by its name), and
its directory is visible there read-only, so files beside it are found by its own path. A bare
name (`python3`, `sh`) is looked up on the guest's `PATH` (`/guest:/usr/local/bin:/usr/bin:/bin`).
The host's `/usr` is visible read-only, so system interpreters and shared libraries work.

A script runs as `execve` runs it: it needs the execute bit, and its `#!` line names the
interpreter (read as the kernel reads it: one optional argument, five nested interpreters at
most). A program that cannot run ends `error`, stop `exec`, with the kernel's errno:

<!-- transcript scripts

The program starts in `/work`, an empty writable directory that is also its `HOME`. Nothing
else of the host is visible unless you give it:

| Flag | What the program gets |
|---|---|
| `--mount SRC:DST` | a host file or directory, read-only, at `DST` |
| `--mount SRC:DST:copy` | a copy of a host directory at `DST` |
| `--work DIR` | `/work` starts as a copy of `DIR` |
| `--work DIR:GUEST` | the same tree at `GUEST` instead (`--work :GUEST`: empty) |
| `--stdin FILE` | standard input |
| `--env K=V` | one environment variable (the rest is fixed: `PATH`, `HOME`, `LANG`, `TZ`, `PATINA=1`) |
| `--cpus N` | the CPU count it sees (default 4, whatever the host has) |
| `--tmpfs-bytes N` | the size of each of its filesystems (`/work`, `/tmp`, copied mounts), all memory-backed tmpfs (`[run] tmpfs-bytes`, default 268435456, 256 MiB) |

A write past that size answers `ENOSPC`, as a full disk does; when one did, `patina run`
names the setting (`sandbox tmpfs full: ...`) and `result.json`'s `tmpfs.enospc` counts the
calls.

When the program runs, opens or looks for a host path the sandbox lacks, `patina run` names it
once and the directory to mount, and a sweep's summary counts the runs that met it:

```text
not in the sandbox: /home/me/app/target/debug/app (the host has it): add --mount /home/me/app/target/debug:/home/me/app/target/debug
not in the sandbox: node, run by name (the host's is /home/me/.local/bin/node, outside the guest's PATH): add --mount /home/me/.local/bin:/home/me/.local/bin and run /home/me/.local/bin/node
```

A mount's `DST` may pass through a symlink inside another mount (a project whose `target` links
into a cache): it is placed where the guest reaches through that symlink. `DST` may be anywhere
but over what the sandbox needs: `/`, `/usr` (and `/bin`, `/lib`, `/lib64`, `/sbin`, its
links), `/proc`, `/sys`, `/dev`, `/etc` and `/tmp` themselves, the files it generates in `/etc`
(`passwd`, `group`, `hosts`, `nsswitch.conf`, `ld.so.cache`, `localtime`, `alternatives`),
and the work tree. Paths under `/etc` and `/tmp` are fine:

<!-- transcript mount-shadow
setup: echo 'me:x:1000:1000::/home/me:/bin/sh' >conf
exit: 2
-->
```text
$ patina run --mount ./conf:/etc/passwd -- /bin/true
patina: error: --mount ./conf:/etc/passwd: /etc/passwd would shadow what the sandbox needs: /etc/passwd is generated by the sandbox
```

The work tree is the one writable, crash-modelled disk: `--work DIR:/var/lib/app` puts it
where a program expects its data, and it is still the working directory and `HOME`. There is
one work tree; other places a program writes (`/tmp`, a `:copy` mount) are writable but not
crash-modelled: a restart finds them as the run began ([Crashes](#crashes)).

Every file in the work tree starts with the same modification time (the simulated clock's
start, 2026-01-01), whatever it was on the host: a run depends on the tree's contents only,
not on when its files were last touched. A program whose behaviour depends on file times
(`make`, `find -newer`, an mtime-ordered cache) sees them all equal. To give it times, set them
inside the run, at the start of the case: `touch -d '2026-01-01 00:00:05' src/b.c && make`
(a `--cases` line, or a wrapper script), and they are part of the run like any other change.
A restart after a crash keeps the times the run gave its files.

The guest sees no network beyond itself: a connection or datagram to another host fails with
`Network is unreachable`, and names resolve from the sandbox's `/etc/hosts` only (`localhost`
works; any other name is not found, and no lookup sends a packet). Servers and clients must
run in the same program or in programs it starts. TCP and UDP work on loopback and on the
addresses `/etc/hosts` gives; multicast, broadcast and raw sockets are refused.

`patina run` prints the outcome and the run directory; when the run is not ok, also the last
lines of the program's stderr and the faults injected, and any calls Patina refused (the
program got an error code for them). The program's full output is in the run directory
(`--out`, default `patina-out/run-SEED`, replaced on each run):

| File | Content |
|---|---|
| `run.json` | the seed, the resolved settings, the program's path and SHA-256 |
| `result.json` | the outcome and everything measured (below) |
| `inc-0/stdout`, `inc-0/stderr` | the program's output; `inc-1/` and on after a crash and restart |
| `inc-0/boundary.log` | every system call and decision, for replay and `patina log` |
| `check.out` | with `--check`, the checker's output ([Checks from outside the program](#checks-from-outside-the-program)) |

A run that never ends fills its logs fast (a livelock writes hundreds of MB a second), so the
logs are limited: `--log-limit MIB` (`[run] log-limit`, default 1024) ends the run
`liveness`, stop `log-limit`, at the record that would pass it, the same record on every
run of the seed. Like a run past `--time-limit`, it is a finding: a sweep groups it, replays it
and matches it against `--known`. The message says what filled it (here `tests/guests/sweep/bugs.c`, whose two
threads each yield until the other is done):

<!-- transcript log-limit

exit: 1
-->
```text
$ patina run --seed 1 --log-limit 8 -- ./sweep-bugs livelock
liveness (log-limit): 8.0 MiB of boundary log (87381 records, 52% scheduling-decision records) reached --log-limit: the program had not finished, likely a livelock under this schedule (a run that is only long, or writes that much to the work tree, needs a higher --log-limit)
run directory: /tmp/patina/patina-out/run-1
replay: patina replay /tmp/patina/patina-out/run-1
explain: patina explain /tmp/patina/patina-out/run-1
```

The starting work tree (`--work`) does not count against it; what the program writes to the
work tree does (the operation log keeps it for crashes).

A full filesystem under `--out` ends the run `internal`, stop `disk-full`. Under `--preempt
branches`, an overflow interrupt from the branch counter that comes later than `[sched]
pmu-margin` ends it `internal`, stop `pmu-late` ([Scheduling](#scheduling)). A guest process killed
by SIGKILL from outside the run (the host's out-of-memory killer, or a kill sent on the host) ends
it `internal`, stop `killed`, naming the process, with its wait status in `result.json`. With `--crash`, a run ends by
checking its operation log: replaying it must give the work tree each incarnation left. A
difference is a Patina defect, never the program's: the run keeps its own outcome (a
violation keeps its label and signature) and says `self-check failed (a Patina defect; ...)`
under it, `result.json` has `self_check` (`verdict` `fail` and the first difference in
`detail`; `pass` when it held) and the exit status is 2. A sweep counts such runs on a line of
their own, keeps their logs, and exits 2 unless a new finding makes it 1. A table of the
runtime's that the program fills with objects it still uses (open descriptors, shared
mappings, files changed and still reachable) ends it `unsupported`, stop `capacity`, naming
the table.

### A configuration file

`patina.toml` in the current directory (or `--config FILE`) holds the same settings; flags
override it, and an unknown key is an error. `--config RUNDIR/run.json` takes every setting
of an earlier run.

```toml
[run]
cmd = ["./acklog"]
cpus = 2

[faults]
crash = "machine:10"
preset = "disk"
fsync-error-permille = 0
```

With that file, `patina sweep` needs no other arguments: it runs seeds 1 to 100 into
`patina-out/sweep`.

## Sweeps

A sweep runs many seeds, in parallel, each a normal `patina run`, and groups the failures
by what failed.

```sh
patina sweep --seeds 1..200 --crash machine --out patina-out/acklog -- ./acklog
```

| Flag | Effect |
|---|---|
| `--seeds 1..200,250` | an inclusive range, a list, or both (default `1..100`) |
| `-j N` | runs at once (default the CPUs, at most 8) |
| `--out DIR` | where runs go (default `patina-out/sweep`) |
| `--keep fail\|checked\|all\|none` | whose logs to keep: those of each group's first three runs, also those of every run a `--check` read (to judge them again, [below](#judging-again)), every run's, none; `run.json` and `result.json` always stay |
| `--max-findings N`, `--budget SECONDS` | stop early |
| `--cases FILE` | one run per line of FILE per seed (below) |
| `--only-case ID[,ID...]` | with `--cases`: only these cases ([below](#test-suites)) |
| `--branch` | with `--crash machine` or `process`: every crash point of each seed (below) |
| `--branch-max N` | with `--branch`: at most N children of each seed, a seeded sample by node and kind of operation (below) |
| `--branch-pairs K` | with `--branch` and nodes: a second node's crash at each of its next K points after each first crash ([below](#several-machines)) |
| `--known FILE` | findings already known: counted, and they do not fail the sweep ([below](#known-findings)) |

`--keep fail` keeps the logs of a group's first three runs (its lowest seeds, the first of them
the one replayed): a bug hit in hundreds of runs would otherwise keep the same evidence hundreds
of times. Its other runs keep `run.json` and `result.json`, and their seeds reproduce them
(`patina run --seed N`, or the group's `rerun:` line). A run kept by `--keep fail` or `checked` whose log is over 4 MiB keeps its first and last MiB
(`boundary.log`, `boundary.tail`); `patina replay` still compares those, and the run's seed
gives the whole log again. A kept run's work trees, most of its size when its program keeps
much on disk, are kept compressed, a few times to tens of times smaller: each incarnation's
(and each node disk's) `live.tree` as `live.tree.zst`, and in a run no checker reads (one that
did not end `ok` on its own) a crash's `post-crash/` as `post-crash.tree.zst`. `patina log
tree` (`--post-crash` for the tree a crash left), `log ops --check` and `log events` read
them as the run left them; a checker, run again or by hand, reads `post-crash/` as it was.
`--keep all` keeps every run as `patina run` leaves it. The sweep prints the bytes it kept,
does not start while `-j` runs at `--log-limit` could fill the filesystem under `--out`, and
stops launching runs when free space falls below that, or when a run finds the filesystem
full.

A sweep directory holds one sweep. It records the program's SHA-256, the command and the
resolved settings (`sweep.json`); the same sweep run again resumes, running only the runs it
lacks (more seeds, or after an interrupt), and any other sweep replaces the directory, as does
an older patina's output (one line says which). A non-empty `--out` that holds no patina output
is refused, never deleted. Edit,
rebuild and rerun the same command: the old runs never mix with the new. The checker is not
part of that identity: a changed checker judges the runs again rather than running them
([Judging again](#judging-again)).

Each group in the summary is one signature: the outcome, what stopped the run, and its first
line of evidence (the failed `always` label with the first line of its detail, the panic or
assertion line or else the last line of stderr, the blocked waits). What names the failure is
kept: the exit status, the signal, the label. Numbers in the program's text (line and column
numbers, addresses, ids, counts, durations) become `N`, and hex ids (six or more hex digits,
letters among them) `H`, so one bug over many seeds is one group.
Absolute paths keep their last three components, in signatures and SDK labels alike (a label
made from a source path is the same in every checkout). With `--cases`, a finding named by a
label (an `always`, a `--check` finding) or by an `INVARIANT` line is one group over every case
it appears in; any other is grouped per case, since an exit status, a signal, a blocked wait
or a runtime's panic text (Go's `index out of range`, an `assert_eq!` without a message) is
the same for unrelated failures. A node's own end (a node's command that fails or crashes, not
the driver's) adds `[node NAME]`, with the name's digits made `N` as well: replicas `n1`, `n2`,
`n3` that fail the same way are one group, while `primary` and `backup` stay two. Which node
crashed, and where, is the faults' doing and not part of a signature. A sweep announces each new group as soon as one of its runs ends (with several jobs, not
always the run of its lowest seed) and replays its lowest seed once; a replay that differs makes the group
`nondeterministic`. `patina report DIR...` prints the same summary for any run directories and
writes `report.json`. A replay or a minimized run is written inside the run it comes from, so it
never counts as one of the sweep's runs.

The summary prints the first three new groups in full (counts, first seed and case, rerun and
replay lines) and every other group on one line, numbered: `#7 [CASE] SIGNATURE   2 of 40
runs   first: seed 3   replayed: identical`; `patina report --group 7 DIR` prints one in full.
`report.json` has every group in full, each with its runs (`runs`: seed, crash point, case,
case id, directory) and `case` set only when all its runs share one. A group whose first run's
message differs from its signature (numbers made `N`, a checker's detail left out, a panic or
stderr line) shows that message or line as written, `example:` (`example` in `report.json`), so
one real instance is in view. A signature is cut at 200 characters, and an `always` detail in it
at 64, on a character boundary; an example at 240.

### Test suites

A test suite is many tests, best run each alone. `--cases FILE` runs every line of FILE once
per seed, each its own run. A line is a whole command: the program and its arguments, quoted
as in a shell (no variables or globs), so one file can name several test programs. Empty
lines and lines starting with `#` are skipped.

```sh
cat tests.txt
```

```text
python3 -m unittest test_store.Store.test_write
python3 -m unittest test_store.Store.test_counter
```

```text
  explain: patina explain /tmp/casedemo/patina-out/sweep/seed-1/2-test_store.Store.test_counter
```

Given a command after `--`, a line is instead put in place of `{}` in it: `--cases names.txt
-- python3 -m unittest {}` runs the same. Each (case, seed) is its own run directory,
`OUT/seed-N/L-NAME`: L the case's line number in the file, NAME its `--name` (below) or a short
form of its last word that is not an option; the file `case` there and the report hold the
whole line. With whole-command lines, a rebuilt program reruns only its own cases when the
sweep runs again.

A case's id is its `--name`, or else its line number: it is `PATINA_CASE_ID` for the checker,
`config.case` in `run.json` (with the whole line, so a replay and `--config run.json` keep
it), `case_id` in `report.json`, and the summary's `first: seed 1, case 2`. `--only-case
ID[,ID...]` runs only those cases, as the same sweep would have run them; an id no line has
is an error. A name is letters, digits, `.`, `_` and `-`, at most 64 characters, not
starting with `.` or `-`, not a number, and unique in the file. A line number moves when a
line is added above it; a `--name` does not, so a corpus that grows names its cases.

A case can bring its own settings: a line whose first word starts with `--` gives `patina
run` flags up to a word `--`, then the case as before. `--work DIR[:GUEST]`, `--mount`,
`--env K=V` and `--stdin FILE` are allowed, parsed as `patina run` parses them, after the
sweep's (a case's `--work` and `--stdin` replace the sweep's, its mounts and variables add to
them); `--name NAME` names the case: its id and its directory. Anything else is a setting of the whole sweep
and refused. A corpus whose cases each have a tree of their own:

```text
--work cases/grep-basic/t:/work/t --env LC_ALL=C -- grep-basic
--work cases/ls-long/t:/work/t -- ls-long
```

```sh
patina sweep --cases corpus.txt -- /h/harness /cases/{}/case.json
```

The settings are part of the case: run again, a sweep keeps the cases whose whole line is
unchanged. A checker (`PATINA_CASE`), the report and a known pattern's `[CASE]` see the line
after its settings (`grep-basic`). Lines are easiest written by a one-line loop, and quoted by
the tool that knows the data, as `jq` does with `@sh`:

```sh
jq -r '"--work \(.tree):/work --name \(.name) -- /h/harness \(.case | tojson | @sh)"' cases.jsonl > corpus.txt
```

A compiled test binary lists its tests; turning the list into lines is one loop. For the
test binaries `cargo test --no-run` builds (the same works for any runner that lists and
selects tests by name):

```sh
for b in $(cargo test --no-run --message-format=json | jq -r 'select(.profile.test and .executable) | .executable'); do
  "$b" --list --format terse | sed -n "s|: test\$||; s|^|$b --exact |p"
done > tests.txt
patina sweep --seeds 1..5 --cases tests.txt
```

### Known findings

A finding already known (being fixed, or a library's to fix) need not fail every sweep.
`--known FILE` (on `sweep` and `report`) names them, one `ID PATTERN` per line:

```text
# ID, then a pattern: * matches any text; a pattern starting with [ also matches the case.
sub-clamps  violation check: wrong-sub: *
!planted    [*planted*] violation check: wrong-*
```

A pattern is matched against the whole of a finding's signature as the report prints it, or,
when it starts with `[`, against `[CASE] SIGNATURE`. Each failing run is matched alone and the
first line that matches names it. A known finding is counted and listed after the new ones,
one line per ID and signature, and is not announced or replayed; only a new finding makes
the exit status 1, and the summary's `findings` counts only new ones. Here `calc OP A B` gets
subtraction below zero and multiplication by zero wrong, a checker names a wrong answer
`wrong-OP`, and the 28 cases include one wrong by construction (the files are in
`tests/docs/fixtures/calc`):

A pattern is matched against the signature, where a number other than an exit status is `N`:
an entry that matches no run, but would with its numbers written that way (or a signature's
`N` written as the entry's digits), says so and names the signature it nearly matched, as
`mul-zero` does here. `[sweep] known = "FILE"` in `patina.toml` (relative to the file) is the
default for `--known`.

A pattern holding `{faults:` is matched with ` {faults: F}` after the signature, F the faults
that fired in the run, sorted and joined by commas (the fault classes that injected, as
`fs-error`, `crash`, `path-swap`, and `point:LABEL` for each SDK fault point that fired; `-`
for none). One oracle can then name two bugs apart by what fired, and by the case's input
when the case line carries it; several lines with one ID are alternatives:

```text
short-write violation check: wrong-output* {faults: *fs-short*}
redirect    [*>*] violation check: SILENT: * {faults: *fs-error*}
calm        violation check: wrong-output* {faults: -}
```

The entries that matched no run are counted on one line (`known: 20 entries matched no run`;
`report.json` lists them under `known.entries`): such a bug may be fixed, and its line can
go. An entry written `!ID` must match: a checker that never fails looks like a
correct program, so a case that is wrong by construction, with a `!` entry for it, proves on
every sweep that the check can fail. When it matches nothing the result is `vacuous` (exit 2).
`patina report --known FILE DIR` applies a file to runs already made, with the same groups
and exit status as a sweep given it; the file is not part of a sweep's identity, so changing
it never reruns anything. `report.json` gives each group its `known` ID (or `null`) and has
every entry's count under `known`.

### Every crash point of a seed

`--branch` with `--crash machine` (or `process`) runs each seed once with crashes on and
never firing, which counts its crash points, then once per crash point with the crash forced
there (`--crash machine-at:N` into `OUT/seed-S@N`), points ascending and seeds in turn. A run
crashed at point N is the same as its seed's run up to N, so the sweep tries every place a
crash could fall in that seed's schedule. `--budget` and `--max-findings` stop it; the same
command again runs only the points not tried yet.

```text
  example: acked-records-kept: 1 acknowledged, 0 stored
  faults in every failing run: crash      in none: -
  rerun:  patina run --seed 1 --crash machine-at:8 -- /tmp/acklog/acklog
  replay: patina replay /tmp/acklog/patina-out/sweep/seed-1@8
  explain: patina explain /tmp/acklog/patina-out/sweep/seed-1@8
```

A run forced to crash at point N that does not crash there ran another prefix than its seed's
first run: the sweep reports it `nondeterministic`, naming both directories.

`--branch-max N` caps the children of each seed at N: a seeded sample in which every node, and
every kind of operation at a point (a write, a rename, the point before an `fsync`, read from
the seed's operation log into its `points.json`), comes up before any comes up twice, and the
rest in proportion. The report says how many of how many it tried; the same command with a
larger N runs only the children the smaller one did not. A run whose points the sweep cannot
place in its log (one whose points count from `setup-complete`) is sampled by node alone. To
branch only over the work after a setup, end the setup with the SDK's `setup_complete()` and
add `--fault faults-after-setup=1`: crash points then count from there.

Each point is tried once, with one draw of what the crash keeps, and "every crash point tried"
covers only the seeds swept. Seeds differ widely in their count (fjall's harness: 4,069 to
23,932 points over three seeds, about 130 ms a run), so give large ones a `--budget` or a
`--branch-max`. Use it when a crash must land in a narrow window and plain crash sweeps find
nothing: on fjall's F2
it finds the window at 4.5 to 7 times a plain sweep's rate per CPU-second, and early windows
(F1, acklog-c) at once. Keep plain sweeps for findings that need variety across seeds, such
as fault plans or a failed fsync at a chosen call: there it finds 5 times less (F3) or
nothing (F4) in the same time (docs/EVIDENCE.md, "Crash-point enumeration").

### If a sweep finds nothing

A sweep that ends all `ok` has looked at as many runs as it had seeds, each one schedule and,
under `--crash`, usually one crash. In order of what helped most on the storage findings
(docs/EVIDENCE.md, "Search quality: fjall F2 and F6"):

- **More seeds.** A crash that must land in a short window (a few crash points out of
  thousands, say between a write and the next fsync) is found in about one seed in several
  thousand, whatever the other settings. Budget for that before changing anything else.
- **Every crash point** (`--branch`, above): a few seeds with each crash point tried once,
  instead of one crash in each of many seeds. It reaches every window of the seeds it runs:
  the first thing to try for a crash window, not for a fault that must vary across seeds.
- **`--buggify`**, and for a fault point that must fire at one particular moment,
  `--fault point:LABEL=1000`: the point is on in every run and fires at every evaluation,
  instead of on in a quarter of runs and firing on a quarter of evaluations.
- **The crash position.** `--crash machine:N` crashes at each crash point with probability
  N per mille, so most runs crash early; a lower N reaches later points and a higher one
  earlier points. To search a region you know (from the `point` of a crash near it, or
  `faults.counts.crash.eligible` of a run without crashes), give the position as a range:
  `--crash machine-at:A..B`.
- **The fault rates**: a preset's ranges (`--faults disk`) and a key's own range.
- **The scheduling settings.** `[sched] preempt-permille` (default 100) is the chance that a
  system call switches threads; `[sched] pause-points = false` stops treating the spin hint
  (`pause`; on arm64 `yield`, `isb`, `wfe`, `wfi`) as a scheduling point; `--cpus N` (default 4) is the CPU count the program sees, which sizes
  its thread pools. Each changes every seed's schedule, so the same seeds then show other
  runs; on their own they did not make the storage findings more frequent.
- **A race with no system call in it.** Threads switch only at system calls, `pause`
  instructions and spin probes. Two threads that race on plain memory with none of these
  between the conflicting accesses always run them in the same order, whatever the seed.
  Rebuild the code with compute points ([Deeper search](#deeper-search-rebuilt-code));
  `--preempt points` switches at the branches, calls and atomics of stock code
  ([Points in stock code](#points-in-stock-code---preempt-points)); branch counters
  (`--preempt branches`, AMD Zen 5 and Arm Neoverse N2 only) switch there too.
- **A deadline that never comes.** In stock code virtual time advances by a fixed charge per
  system call and when every thread sleeps, not with computation, so neither `--time-limit`
  nor the program's own deadline cuts a CPU-bound loop; `--timeout` (wall seconds) does, as
  `timeout`. Rebuilt code, and stock code under `--preempt points`, is charged 1 ns per event
  and is cut where the deadline falls due; `--preempt branches` charges time per branch.

## Faults

Faults are drawn from the seed like everything else. A preset turns on a class with rates
that are ranges; each seed picks a value in each range, so one sweep covers gentle and harsh
settings.

| Preset | Settings |
|---|---|
| `--faults disk` | `fs-error-permille=0..5 fs-short-permille=0..20 fsync-error-permille=0..3 fs-delay-permille=0..20` |
| `--faults net` | `net-delay-ms=0..50 net-chunk-max=1..65536 net-reset-permille=5..50 net-connect-refuse-permille=0..10 net-drop-permille=0..50 net-dup-permille=0..20 net-reorder-permille=0..50` |
| `--faults all` | both, plus `mem-error-permille=0..2` |
| `--faults cluster` | with nodes only: `net`'s keys, partitions, pauses, clock skew and machine crashes ([Several machines](#several-machines)) |

`--fault KEY=VALUE` sets one key and replaces the preset's value for it; `patina run --help`
lists every key.

A class a preset turned on that had nothing to act on in any run of a sweep (datagram faults
for a program that only uses TCP, disk faults for one that writes nothing under `/work`) is
listed on one line and does not make the sweep `vacuous`; a class you named with `--fault`
(or a `[faults]` key) that never applied still does, since you asked for it:

<!-- transcript not-applicable

exit: 1
-->
```text
$ patina sweep --seeds 1..20 --faults net --out patina-out/tcp -- ./sockets chunk correct
...

```

Over TCP, `net-chunk-max` splits each delivery into pieces of at most that many bytes (a
range draws a size per seed, log-uniformly, so about one seed in four of `1..65536` delivers
at most 16 bytes a piece, and one in 17 a byte at a time). The pieces of one delivery follow
each other by 1 to 10 µs of virtual time, so a seed's throughput over one connection in `--faults net` is about 180 kB/s at the least, a
median of about 4 MB/s and 6 MB/s at the 90th percentile (256 KiB sent, docs/EVIDENCE.md,
"Net preset shaping"); a protocol timeout shorter than its message takes at that rate is
then a finding about the timeout. For the harsh link, name the keys: `--fault
net-chunk-max=1 --fault net-delay-ms=10..50`. Since 0.13.0, a run with `--faults net` or `all`, or
with a `net-chunk-max` range, has another digest than under 0.12 when it splits a TCP delivery
(the chunk size and the gap are drawn anew); every other run keeps its digest. Disk faults act on files under `/work`, pipes and unix sockets; an injected
error is one Linux can return for that call on that object. A failed write-back
(`fsync-error-*`) is reported as Linux reports one: once to each open file description,
also to a descriptor opened after it if nobody was told yet, never by a `sync_file_range`
that does not wait; the data it held is lost to a machine crash even if a later `fsync`
succeeds (ARCHITECTURE.md, "The fsync-error model"). Network faults act on TCP
connections and UDP datagrams: a reset is drawn on each piece of data a program sends, so a
long-lived (keep-alive) connection meets one; a refusal or timeout is drawn once per connect.
Each datagram gets its own delivery time in the `net-delay-ms` range, so datagrams already
arrive out of order within that jitter; `net-drop-permille`, `net-dup-permille` and
`net-reorder-permille` (held back past later datagrams) are drawn per datagram, and a
datagram due inside a `net-blackout` window is lost. `net-blackout=START+LENGTH[:PORT]`
holds TCP deliveries and loses datagrams for LENGTH ms from START ms of virtual time (only
those from or to PORT, if given), and keepalive probes go unanswered in it, as across a cut; START and LENGTH are each a number or a range drawn per
seed (`--fault net-blackout=0..60000+1000..10000` puts a window of 1 to 10 s somewhere in
the first minute). Before 0.16 it was `net-partition`, a name that is refused now: a partition
is a cut between nodes ("Several machines"). A receive queue past the socket's
`SO_RCVBUF` drops datagrams with no fault, as Linux does. A request/response protocol with
no retry, run with `--fault net-drop-permille=50`:

```text
liveness (deadlock): every thread is blocked with no deadline: slot=0 tid=2 wait=io gen=19 fd=3 dir=in call=poll nfds=1 deadline=none; slot=1 tid=3 wait=io gen=19 fd=3 dir=in call=recvfrom nfds=1 deadline=none
faults injected: 1 (net-drop 1)
last injected:
  seq 147 t=100000ms net-drop dropped datagram 9 from :32769 to :32768 (3 bytes)
```

`mem-limit-mb=N` makes memory requests past N MiB fail with `ENOMEM`. `result.json`'s
`faults.counts` gives per class the calls (or sends, connections, deliveries, datagrams) it
was drawn on and the faults it
injected; `faults.injected` is their sum.

### Path swaps

A program that checks a path and then uses it by name assumes nothing changed it in between.
Another process can: replace the file with a symlink, rename a directory into the path, or
take the file away. `--fault path-swap-permille=P` makes that change itself. When a process
uses a path under the work tree (`open`, `exec`, `chdir`, creating, removing, renaming or
changing it by name) that it checked within its last 16 checks (`stat`, `lstat`, `access`,
`readlink`, `open`) or that lies below one, Patina changes one component of the checked path
before the use, at rate P per such use:

- it becomes a symlink: to a path outside the work tree (`/etc/passwd` for a file, the work
  tree's parent for a directory), to another entry of its directory, or to nothing;
- another entry of its directory is renamed into its place;
- it is renamed away.

The original goes to `.patina-swap-SEQ` in its directory, and half the swaps are put back right
after the use (as far as the use left them; never after an `exec`). A swap is made as a process
with the program's uid would make it, only inside the work tree. `path-swap-at=N` swaps at the
N-th eligible use (`A..B` searches a range).

Path swaps are in no preset. A program that owns its directory is entitled to assume nobody
else renames things in it, so a finding is a bug only where the program must withstand another
writer: a server reading a shared directory, a tool that enforces which paths a user may touch.
`examples/serve-c` checks a file with `lstat` and then opens it by name:

<!-- transcript path-swap

exact-only: one seed's run
-->
```text
$ patina run --seed 4 --fault path-swap-permille=300 -- ./serve

faults injected: 1 (path-swap 1)
last injected:
  seq 83 t=100000ms path-swap /work/public/report.txt became a symlink to /etc/passwd between newfstatat (seq 82) and openat
run directory: /tmp/serve/patina-out/run-4
replay: patina replay /tmp/serve/patina-out/run-4
```

In `result.json` each swap names its `object`, the `swap` (`symlink`, `rename`, `remove`), its
`target`, the checking call (`after`, `after_seq`) and whether it was `put_back`; `patina log
ops` lists its renames and symlinks at the use's seq.

### Crashes

`--crash machine` crashes the whole program at a seed-chosen point and starts it again with
the same arguments, on what had reached the disk: data never synced may be gone, renames and
creations may be undone. `--crash process` kills the processes but keeps what they wrote, as
an operating system does when a program dies. The default rate is 3 per mille per crash
point (`--crash machine:10` for 10); `machine-at:N` crashes at the N-th crash point of the
first run (counted from the `setup-complete` mark under `faults-after-setup`). Crash points
follow each change to `/work` and precede each sync, so one call can hold several (an
`fsync`: before it and after it). A run with `machine-at:N` is the same as the run without
it up to that point. `crashes[].point` in `result.json` (and `point=` in `last injected:`)
is a crash's ordinal within its incarnation, so a crash of incarnation 0 that a sweep found
can be moved one point earlier or later with `-at`. Like the other `-at` settings (`fsync-error-at=N`,
`fs-error-at=CLASS:N`, `mem-error-at=N`), N may be a range `A..B`: each seed picks its own
point in it, so a sweep searches the region. An N past the run's last crash point never
fires: the run ends as it would without the crash, with `faults.counts.crash.injected` 0.

A program under `--crash` must be restartable: on start, it recovers its state from `/work`
and checks it. `PATINA_INCARNATION=K` is set after the K-th restart. `examples/acklog-c`
shows the shape:

<!-- transcript crash

exit: 1
exact-only: one seed's run
-->
```text
$ patina run --seed 3 --crash machine -- ./acklog
violation (always): acked-records-kept: 23 acknowledged, 0 stored
faults injected: 1 (crash 1)
last injected:
  seq 124 t=100000ms crash kind=machine point=97 object=/work/data.log lost: 0 missing, 1 changed, 0 back
run directory: /tmp/acklog/patina-out/run-3
replay: patina replay /tmp/acklog/patina-out/run-3
explain: patina explain /tmp/acklog/patina-out/run-3
```

What survives a machine crash follows `ext4-ordered` by default; `--fault fs-model=posix-strict`
(`[faults] fs-model = "posix-strict"`) allows everything POSIX allows, which loses more.

`ext4-ordered` stands for ext4 mounted with its defaults (`data=ordered`, delayed allocation,
`auto_da_alloc`, a journal commit every 5 s). Names, sizes and attributes reach the disk only
at a commit: at an `fsync` of a file or directory the running transaction holds, at `sync`,
once the transaction is 5 virtual seconds old, and at one seed-chosen moment after the last of
those. A commit is all or nothing and they come in order, so creations, renames and unlinks
survive in the order they were made, across directories too. A file's new size reaches the
disk with its data (delayed allocation: written back at its `fsync`, at `sync`, or at the
seed-chosen commit), with one exception: a write that extends a file inside its last
allocated 4 KiB block raises the size at once, so a crash can keep the larger size with the
new bytes reading as zeros, as ext4 does. A rewrite of a block that was already on disk goes in place: each such block survives
old or new, on its own. Replacing a file by `rename` over it, or after truncating it to zero,
writes the new data first (`auto_da_alloc`). `fdatasync` is an `fsync`.

`posix-strict` keeps only what POSIX promises: data and attributes of a file after its own
`fsync` or a `sync`, a name after an `fsync` of each directory it changes or a `sync`. Every
other change is kept or dropped on its own draw, in any combination that leaves a consistent
tree, so unlinks in two directories can survive one without the other. No real filesystem
reorders this freely: a finding only `posix-strict` gives is a program relying on more than
POSIX promises, not a state ext4 produces.

A restart starts the program as a new boot would, with the arguments and environment it had
(plus `PATINA_INCARNATION`). What carries over:

| | after `--crash process` | after `--crash machine` |
|---|---|---|
| `/work` | as it was | what the model keeps |
| a file's modification time | as it was | as it was at the crash, whatever data the model keeps |
| `/tmp`, other writable places | empty again | empty again |
| System V shared memory | kept | gone |
| process IDs | the same numbers again, from the first | the same |
| the clock | 1 to 61 s later (`restart-gap-ms`) | the same |

A file's access, change and birth times read as its modification time after a restart. Times
are not crash-modelled: ext4 too can keep an inode's new time with its old data. Process IDs
repeat on purpose: it is the worst case for a lock file that names its holder, whose dead
holder now has the PID of a live process of the new incarnation. A program that checks
whether a lock's PID is alive fails on every restart; when every restart fails the same way,
check this first.

A run starts at most 4 incarnations: the last one never crashes, so a program restarts at
most 3 times. `--fault max-incarnations=N` (`[faults] max-incarnations = N`) changes that.
Each restart begins 1 to 61 s of virtual time after the crash, drawn from the seed;
`--fault restart-gap-ms=A..B` draws it in A..B ms instead (`5000..5000` for exactly 5 s), for
a program whose recovery depends on how long it was down (leases, timeouts).
The other faults stay on in the incarnations after a crash, so recovery code meets them
too (`patina minimize` shows whether the crash alone fails it).

## Checks from outside the program

A program that exits 0 can still be wrong: it acknowledged a record a crash then lost, or
wrote the wrong file. `--check 'CMD ARGS'` (on `run`, `verify` and `sweep`; `[run] check =
"CMD ARGS"` in `patina.toml`) judges each run from outside, with no change to the program:
after a run that ended `ok`, Patina runs `CMD ARGS RUNDIR` on the host.

| The checker gets | |
|---|---|
| `RUNDIR` | its last argument: `run.json`, `result.json`, per incarnation `inc-K/stdout`, `stderr`, `post-crash/` |
| working directory | where patina was started (recorded in `run.json`); paths in `CMD ARGS` are relative to it |
| `PATINA_SEED`, `PATINA_EXIT` | the seed; the program's exit status |
| `PATINA_CASE`, `PATINA_CASE_NAME`, `PATINA_CASE_ID` | in a sweep with `--cases`: the case's line (after its settings), its directory `L-NAME`, and its id (its `--name`, or its line number) |
| `PATINA` | the `patina` that runs it, for `"$PATINA" log events RUNDIR` whatever the `PATH` |

| It answers | The run |
|---|---|
| exit 0 | stays `ok` (`check.verdict` `pass`) |
| exit 1 | `violation`, stop `check`, named by the first line of its stdout, `LABEL: detail` or `LABEL [KEY]: detail` |
| exit 77 | stays `ok`, not judged (`not-judged`; the first line says why, `CLASS: detail`) |
| any other exit, a signal, cannot be started, still running after `--check-timeout` seconds (default 60) | `error`, stop `check`: a broken checker is never a pass |

`LABEL: detail` is treated as an SDK `always` label and detail are: the label is kept as
written, digits included, and numbers in the detail become `N`, so a sweep groups one bug once
however many runs hit it; put what tells findings apart, as the leg or the oracle's variant, in
the label (`SILENT-err7: ...`), not the detail. Names in the detail (a file, a key) are kept as
written and split the group by name: write the class of the problem on the detail's first line
and the specifics after it, or use a key (below). When the checker knows what tells its findings
apart, it says so with a key: `LABEL [KEY]: detail`, LABEL one word and KEY anything up to the
`]`, groups by the label and key as written, and the detail does not enter the signature at all
(`wrong-output [grep-basic]: got 3 lines, want 4` is the group `wrong-output [grep-basic]`,
with that line as its `example:`). The signature keeps the first 200 characters of
that line (an `always` detail: its first 64). The run directory's own path in that line is written `RUNDIR`
(a replay's is elsewhere). One run is one finding: a checker that sees several problems prints
the most specific first, and the rest go to `check.out`.
The checker's stdout, then its stderr, are in `RUNDIR/check.out`; `result.json` has its
verdict under `check`. The checker is your program, run as you on the host: Patina does not
sandbox it or limit its network. `CMD ARGS` is split into words as a `--cases` line is
(quotes, no expansion); no shell runs unless you name one (`--check 'sh -c "..."'`). Its time
limit is `--check-timeout` (60 s), counted from its own start, apart from the run's
`--timeout`; it is killed if patina is, and a run
directory left by a patina stopped during the check says `error` (`check.verdict` `pending`).
`verify --vary env` changes the environment variables, umask and limits the checker inherits
too. A run that did not end `ok` (a failure, a
crash, a hang) is a finding already and its checker is not started.

Under faults a correct program often fails cleanly: it reports the error and exits 1. `--ok-exit
N[,N...]` (`[run] ok-exit = [1]`) names the exit statuses that mean that (`--ok-exit any`:
every status, for a reference sweep of another program whose failures are its output): such
a run ends `ok`,
stop `ok-exit`, so the checker judges it too and gets the status as `PATINA_EXIT`;
`result.json` keeps it as `guest.exit`, and `run.json` and the rerun line carry the list. A
program killed by a signal is a `crash` whatever the list holds, an exit status not in it is
still a `failure`, as is a listed status after the program wrote a line starting `INVARIANT `
to stderr, and a failed `always` is still a `violation`. A sweep counts these runs apart
from the passes (`31 ok (4 by --ok-exit)`, `ok_exit` in `report.json`), so a sweep in which
every run failed cleanly says so. Name only statuses the program documents as a clean
failure: a program that exits 1 both for an error it handled and for an uncaught exception
passes both with `--ok-exit 1`; a checker can still fail such a run on its stderr. A Rust
panic exits 101, so `--ok-exit 1` leaves panics findings.

A status the program returns only for an error a fault caused can say so: `--ok-exit
N:CLASS[,CLASS...]` (`[run] ok-exit = [2, "1:fs-error,fsync-error"]`) allows N only in a run
where one of those fault classes injected (a class from `--faults`, `crash`, `path-swap`, or
`point:LABEL` for an SDK fault point that fired); elsewhere N is a `failure` as before. The
condition is kept in `run.json` and the rerun line. `examples/upcase-c` (below) exits 1 on any
error:

A checker must be a function of the run directory and of files that do not change. One that
reads the wall clock, the network or a reference that moves answers differently for the
same run: a replay whose logs are identical to the run's while the checker's verdict differs
ends `error`, stop `check-unstable` (not `nondeterministic`, which is a Patina bug), and a
sweep's group whose replay did so is `error`. The checker's output never enters the run's
logs or digest: a run judged `pass` has the digest it has without `--check`.

What a checker can read after a crash: `inc-K/stdout` and `stderr` (what each incarnation
wrote before its crash), `inc-K/post-crash/` (the tree a machine crash left, the next
incarnation's starting disk; a process crash loses nothing and has none) and `result.json`'s
`crashes[]`. It runs once, after the last incarnation. With `--cases`, each case's run has its
own check; under `--branch` each base and each child is judged.

A property of what the program did, rather than of what it left, reads the event stream
([The event stream](#the-event-stream)): a few lines of `jq` over `patina log events RUNDIR`.
Two examples ship beside `acked-kept`:

- `examples/checks/confined [-r PREFIX]... ROOT... RUN`: every change to the work tree (`op`
  events other than `close` and the syncs) is on a path under a root; in a run made with
  `--log-paths`, every file opened is too, or under a prefix it may read (`-r /usr -r /etc`
  for a dynamically linked program), judged on the path the open walked. A read-only open of
  a directory above a root (to fsync it after a create or rename) is allowed.
- `examples/checks/no-symlink-escape ROOT... RUN`: in a run made with `--log-paths`, every
  file opened resolves under a root, symlinks followed: a link planted in a directory the
  program serves, or one a path swap makes between a check and the open
  ([path swaps](#path-swaps)), does not take it elsewhere. Without the flag it does not judge
  (exit 77).
- `examples/checks/synced-before-mark FILE PREFIX RUN`: for a program that marks each
  acknowledgement with the SDK's `mark` (`mark("ack 17")`), no write to `FILE` is unsynced at
  a mark whose label starts with `PREFIX`; other marks are ignored.

```sh

    | . as $e | (.path, .to) | strings | . as $p
    | select(all($roots[]; . as $r | $p != $r and ($p | startswith($r + "/") | not)))
    | "\($e.op) \($p) (seq \($e.seq))") // empty'
```

an oracle a rule. The runs need not be made again to be judged again, only kept. Here

the checker of `tests/oracles/06-triage.sh`, which skips the cases `chk/expected.txt` names:

`patina recheck DIR...` runs the checker again on each run's kept logs and rewrites only its
verdict: `check` in `result.json` (and the outcome, stop, message and signature that follow
from it), the checker `run.json` records, `check.out`. The run's digest, logs, faults and SDK
results stay as they were, and a run judged as before is rewritten byte for byte as it was.
Without `--check` or `--check-serve` it judges each run with the checker the run records,
read again from its file; with one, every run gets that checker. It then prints the report
(`--known`, `--allow-unmet` as for `report`) and, given one sweep directory, writes its
`report.json`. A run that did not end `ok` stays a finding, as in a sweep. A replay made
before a recheck that changed the verdict is removed: it judged with the earlier checker.

`--keep checked` keeps the logs of every run the checker read, cut as `--keep fail` cuts
them: for a corpus of short runs, about what `--keep all` keeps (each run's `inc-0` with its
stdout, stderr and log), which is what makes judging again possible. A run whose logs were
pruned (`--keep fail`: an `ok` run, or a finding past its group's first three) has nothing to read: a recheck names it, leaves its
verdict as the earlier checker's, and does not count that as a failure; the report then says
its verdicts are of two checkers (`check.checkers` in `report.json`):

```text
recheck: seed-1/2-readf: its logs were pruned (a sweep's --keep fail): not judged again; its verdict is the earlier checker's
...
recheck: judged 2 runs again in 0.0s; 6 pruned, left as they were (a sweep with --keep checked keeps what a checker reads)
patina report: 8 runs, 2 findings in 1 group, 6 ok
check: these verdicts are of 2 checkers (check.checkers in --format json): patina recheck judges them again with one
```

The same sweep run again with a changed checker does the same before it runs anything: a run
whose recorded checker differs (its words, or its file's SHA-256), or whose verdict was left
`pending`, is judged again from its logs, and run again only when they were pruned; one line
says which. A run judged again counts as one the sweep finished: `--keep` prunes or keeps its
logs by the new verdict, and its findings count toward `--max-findings`. Patina knows the checker's own file only: a table or a reference it reads is not
tracked, so after editing those, run `patina recheck`. With `--check-serve` the servers are
started once per job, as in a sweep.

### A checker that serves

A checker in a scripting language spends most of its time starting: an interpreter and its
imports cost 30 to 100 ms, where a short run costs 10 to 30. `--check-serve 'CMD ARGS'` (`[run]
check-serve`) starts it once per sweep job instead, with `PATINA_CHECK_SERVE=1` and no run
directory, and asks it about each run on its stdin, one JSON line, `{"rundir": DIR, "env":
{"PATINA_SEED": ..., "PATINA_EXIT": ..., "PATINA_CASE": ..., "PATINA_CASE_NAME": ...,
"PATINA_CASE_ID": ...}}`. It answers one line on its stdout:

| It answers | The run |
|---|---|
| `pass` | stays `ok` |
| `fail LABEL: detail`, `fail LABEL [KEY]: detail` | `violation`, stop `check` |
| `skip CLASS: detail` (or any reason) | stays `ok`, not judged |
| anything else, two lines, a line before it was asked, nothing within `--check-timeout`, or it ended | `error`; the server is killed and the sweep starts another for the job's next run |

A line carries no request number: an answer written out of turn is found at the job's next
request at the latest, so the run it lands on may take it for its own, but the sweep then has
an error and never ends clean. A server must not leave processes of its own outside its
process group: those are not ended with it.

Everything else is as for `--check`: the verdicts, `check.out` (the answer, then what the
server wrote to stderr meanwhile), `check-unstable`, `pending` for a sweep stopped mid-check,
and the `check:` line. `run`, `replay` and `minimize` start a server for their one run. A
server must judge each run as a new process would: state carried from one request to the next
makes a replay `check-unstable`. The same file can do both; `examples/checks/same-output.py`
ends:

```python
if os.environ.get("PATINA_CHECK_SERVE"):
    for line in sys.stdin:
        req = json.loads(line)
        os.environ.update(req["env"])
        code, say = check(sys.argv[1], req["rundir"])
        print({0: "pass", 1: f"fail {say}", 77: f"skip {say}", 2: f"error: {say}"}[code], flush=True)
```

A run started per run costs less when the interpreter is named by its path with no wrapper
in front of it (`/usr/bin/python3 -I`, not a version manager's shim): on 300 runs of a Python
checker that imports a 2,500-line oracle module, the sweep took 1.9 s without a check, 7.2 s
through a shim, 4.3 s with the interpreter's path, and 2.3 s serving.

### Triage with a known table and an expected-differences table

A corpus compared with a reference turns up three kinds of difference: bugs, bugs already
known, and differences that are correct (the reference is another implementation, or an older
version). Keep each in its own table and judge again as the tables grow:

1. Sweep the reference once, `--seeds 1 --keep all`, and the program with `--keep checked`.
2. The checker reads a table of expected differences (case ids, one per line) and exits 77
   with `expected: case ID differs by design` for a case it names: not judged, counted under
   `expected`, never a finding. It reports any other difference keyed by the case,
   `wrong-output [$PATINA_CASE_ID]: got ...`, so each case is one group and `example:` shows
   what it got.
3. Read the groups. A correct difference: add the case id to the table. A bug already known:
   a `--known` line for it (`[*grep-basic*] violation check: wrong-output*`). A new bug:
   reproduce it with the group's `rerun:` line, which runs the case alone.
4. `patina recheck --known known.txt OUT` after each table edit: no run is made again, and the
   report shows what is left. Keep one `!ID` entry for a case wrong by construction, so a
   checker that stopped failing is caught.

The checker of `tests/oracles/06-triage.sh` is such a checker, in eight lines of shell.

## Several machines

A run can hold several machines, called nodes. The command after `--` is the **driver**,
node 0: it is never faulted, and the run ends with its exit status, as a run without nodes
does. Each `[node.NAME]` table in `patina.toml` adds a node whose first process starts with
the run:

<!-- transcript nodes-kv
dir: /tmp/nodes

setup: printf '[node.primary]\ncmd = ["python3", "/guest/kv.py", "primary"]\n\n[node.backup]\ncmd = ["python3", "/guest/kv.py", "backup"]\n' >patina.toml
-->
```text
$ cat patina.toml
[node.primary]
cmd = ["python3", "/guest/kv.py", "primary"]

[node.backup]
cmd = ["python3", "/guest/kv.py", "backup"]
$ patina run --mount g:/guest -- python3 /guest/kv.py driver

$ cat patina-out/run-0/inc-0/stdout

healed: converged on [('cut', 'v-cut'), ('k0', 'v0'), ('k1', 'v1'), ('k2', 'v2')]
```

`kv.py` (in `tests/guests/nodes`) is a key-value store whose primary sends each write to the
backup and answers once the backup has acknowledged it. The driver writes and reads back from
the backup, cuts the link between the two, sees the next write wait and the backup fall behind,
heals the link, and checks that both sides agree. With the backup acknowledging before it
applies, the read-back finds a stale value in most seeds (`tests/nodes/02-kv.sh`).

A node's keys: `cmd` (required), `env` (a table, added to the run's), and `work = "DIR[:GUEST]"`
(the host directory its work tree starts from, and the tree's guest path; default `/work`,
empty). For a quick case, `--node NAME='CMD ARGS'` on the command line adds a node with just
a command (split into words as a `--check` line is: quotes, no expansion), after the file's:
`patina run --node db='redis-server --bind 0.0.0.0' -- ./test.sh`. A node whose command cannot
run ends the run at once (`exec`, naming the node). Nodes start in the order the file lists them, one after another, before the driver
runs; up to 15. Their names are letters, digits and `-`, starting with a letter; `driver` is
the driver's, and `rest`, `localhost` and `sim` are taken.

**What a node has of its own.** A work tree, `/tmp` and `/dev/shm` (each an empty tmpfs, the
work tree filled from `work`), its hostname (its name; the driver's is `driver`), System V
shared memory, a TCP and UDP port space, a loopback, and the address `10.0.0.(k+1)`: the driver
is `10.0.0.1`, the first node `10.0.0.2`. `/etc/hosts` names every node, so `primary` resolves
on all of them. The rest of the sandbox (`/usr`, `/guest`, the mounts) is shared and read-only
on the nodes: what the driver writes there, nodes see, a deliberate channel from the driver to
the nodes and the only one besides the network. The driver's work tree is not visible to
them. A node's process sees only its own
node's processes: another node's are `ESRCH` to `kill`, `getsid`, `getpgid` and the other calls that take a
pid, and absent from `/proc`. Each node's
first process starts with the driver's process state (umask, limits, signals) and the
environment `PATINA_NODE=NAME` and `HOME` (its work tree). Its output is in
`RUNDIR/node/NAME/inc-0/`, beside the driver's `inc-0/` (`inc-K/` for its K-th restart, below).

**Addresses.** A listener on `0.0.0.0` or the node's own address is reachable from every node
at that address; one on `127.0.0.1` only from its own node. Connections show the nodes'
addresses at both ends (`getsockname`, `getpeername`, `accept`). Binding another node's address
answers `EADDRNOTAVAIL`. UDP works between nodes as on one machine (unicast; a datagram
shows its sender's node address); broadcast and multicast are refused as without nodes.
Abstract `AF_UNIX` names are each node's own: two nodes may bind the same name, and a node
connects only to its own (the kernel holds each under a prefix that names the node, which
names read back never show; an abstract name is 11 bytes shorter at most). An autobind, and
the one the kernel makes for an unbound socket with `SO_PASSCRED`, is a name of its node too.
`AF_UNIX` sockets at paths work, each in its node's own files.

**Control from the driver.** The driver acts on the network with control calls: `patina ctl
WORDS` in a script (`patina` is at `/opt/patina/bin/patina`, on the `PATH` of a run with
nodes), `patina.control("WORDS")` in Python, `patina_control("WORDS")` in C (`patina.h`),
`patina_dst::control("WORDS")` in Rust and `patina.Control("WORDS")` in Go.
Each is a call the log records: `patina log events` shows it as an `sdk` event with `op`
`control` and the words in `text` (`mark` words included: they do what the SDK's `mark`
does, but the event is this one, not a `mark` event), followed by the `net` or `node` event
of what it did.

| Words | |
|---|---|
| `net cut A B` | cut both directions between the node sets `A` and `B` |
| `net cut --from A --to B` | cut one direction: what `A` sends to `B` is held |
| `net heal A B`, `net heal --from A --to B` | heal those links |
| `net heal` | heal every cut |
| `node kill NAME` | crash node `NAME`'s machine (below) |
| `node kill NAME --process` | kill every process of node `NAME` (below) |
| `node start NAME` | start the command of node `NAME`, which is down, again |
| `node pause NAME`, `node resume NAME` | freeze node `NAME`'s machine, and let it run again ([Pausing a node](#pausing-a-node)) |
| `clock step NAME +90s` | move node `NAME`'s realtime clock (`+Ns`, `-Ns`, `+Nms`, `-Nms`; [Each node's clock](#each-nodes-clock)) |
| `mark LABEL` | as the SDK's `mark` (any node) |

A set is node names joined by commas (`driver` included), or `rest`: every node the other set
does not name. Only the driver's processes may use `net` and `node`; a node's get `EPERM`
(`patina ctl` says why and exits 2); so may `clock`. An unknown name is `ENOENT`, other words
`EINVAL`.

**What a cut does.** A node's traffic to itself is never cut. Across a cut link no TCP data is
lost and nothing fails at once, as with a cable pulled out for a while: bytes and the closing
of a connection that a cut direction carries are held; the receiver's reads wait, and the
sender's writes go on until its buffer fills. A heal delivers what was held in order, each item after the link's
delay from the heal. A direction still cut after 924.6 s of virtual time (the kernel's default
retransmission limit, or the sender's `TCP_USER_TIMEOUT`) gives up: the
sender's next call fails with `ETIMEDOUT` and the connection is reset. A connection with
`SO_KEEPALIVE` probes as Linux does (`TCP_KEEPIDLE`, `TCP_KEEPINTVL`, `TCP_KEEPCNT`, default
7200, 75 and 9 s and probes): a side whose probes go unanswered across a cut for its budget
(idle + count x interval, or `TCP_USER_TIMEOUT`) fails with `ETIMEDOUT`, even if it only
reads; a cut shorter than that changes nothing. Each unanswered probe is a `probe` event. A
connect across a cut
(in either direction) retries at 1, 3, 7, 15, 31 and 63 s and fails with `ETIMEDOUT` at 127 s
(the kernel's default 6 SYN retries, or the socket's `TCP_SYNCNT`); healed in
between, it completes at the next retry, refused then if nothing listens. A datagram sent while
its link is cut is lost.
`result.json`'s `nodes.net` counts the cuts, heals and held directions and lists the links still
cut at the end.

**In the logs.** `result.json` has `nodes`: `list` (each node's `name` and `address`; the
others' first process `pid` and `end`: `running`, `{"exit": N}` or `{"signal": N}`) and `net`.
`patina log events` names each thread's node (`node`) and has two more types, `node` and `net`
(below); `patina log dump` ends each record with `node=NAME`; `patina report` says which nodes
its runs had.

### Faults between nodes

The network's faults act between nodes, drawn by the seed as on one machine. The link faults
(`net-delay-ms`, `net-reset-permille`, `net-connect-refuse-permille`, `net-chunk-max`,
`net-drop-permille` and the rest, `net-blackout` included) act on a link, a direction between
two nodes, as `net-links` says: `nodes` (the default) the links between nodes other than the
driver, `driver` also the driver's, `all` also each node's traffic to itself. A link they do not
act on carries the default delay and nothing else, so by default the driver is a client and
health checker the network never fails; with `net-links=driver` it is one the network can cut
off, partitions included. The driver's control calls are not network traffic: they answer
inside a partition that cuts the driver off. Each draw is keyed by its connection or datagram,
so a direction of a pair of nodes gets its own.

**Partitions** are the seed's cuts. `partition-gap-ms=A..B` turns them on: after a gap drawn
from `A..B` the seed draws a shape and two sides of the nodes the link faults act on, cuts the
links between them for `partition-ms` (a range, default `1000..30000`), heals them, and draws
the next gap. A cut is a script's cut: held, not lost, but for datagrams. The shape is drawn
from those the nodes fit:

| Shape | Cuts |
|---|---|
| `split` | both directions between two sides, each of one node or more |
| `isolate` | both directions between one node and all the others |
| `oneway` | only what one side sends to the other |
| `bridge` | both directions between two sides, but for one node that still reaches both (three nodes or more) |

`--faults net` (and `all` and `cluster`) adds `partition-gap-ms=5000..60000` and
`partition-ms=500..20000` in a run with at least two nodes the link faults act on; a run
without nodes gets what it got before. A partition key in a run without two such nodes is refused. A partition that a sweep's
preset turned on and that never held, lost or kept back any traffic is `not applicable` in the
report, as other classes with nothing to act on are.

Every cut and heal is in the logs: `result.json`'s `nodes.partitions` (each partition's ordinal,
shape, sides, `from_ms` and `to_ms` in the virtual time events use, `null` while in force at
the end, and whether it `acted` on traffic), a `net` event with `by` `seed` (or `script` for a
control call), and a `partition` fault in `faults.counts`. A failing run's summary says which
partition was in force at the end, or the last one. `patina report` counts them over a sweep:

### Killing and restarting a node

A node's processes can be killed and its command started again, by the driver or by the seed.
This is a process kill, as `kill -9` of everything the node runs; a crash of the node's
machine, which also loses what it had not synced, is the next section's.

`patina ctl node kill NAME --process` (or `patina.control("node kill NAME --process")`) kills
every process of node `NAME` at once; `node start NAME` starts its command again. A kill of a
node that is down answers `EALREADY` (and cancels a restart it had coming); so does a start
of one that is up or already starting, and a start past the 64th incarnation answers `EAGAIN`. What the node's peers see is what they see when a machine's processes are
killed: its connections end (a peer reads end of file, or `ECONNRESET` if data was in
flight), its listeners are gone, so a connect to it is refused while it is down, and the
datagrams sent to it are lost. Its work tree, `/tmp` and `/dev/shm` stay as its processes left
them: the restarted command finds them, starts in the same hostname and addresses, and has
`PATINA_INCARNATION=K` in its environment (K counts its starts from 0; the first start has
none). Each start's output is in `RUNDIR/node/NAME/inc-K/`.

**The seed's kills.** `--crash process` kills nodes at times the seed draws, and restarts
them (a kill or restart that falls while a process or thread is being created waits until it
exists, so a new child is killed with its parent): every node but the driver (`--crash process@a,b` only those). After each start of a
node, `crash-gap-ms=A..B` (default `5000..60000`) is the virtual time to its next kill; after
a kill, `down-ms=A..B` (default `1000..5000`, short beside the gap, so that several nodes are
seldom all down at once) the time it stays down before its restart.
`max-incarnations=N` stops the kills once a node has started N times (each node counts its
own). In a run with nodes `--crash` means this, its machine form
(`--crash machine[@a,b]`, next section) or a machine crash at a node's crash points
([At a node's crash points](#at-a-nodes-crash-points)); `restart-gap-ms` is refused, and the
driver is never killed.

**What keeps a run alive.** When every thread waits with no deadline, the run goes on to the
next event that can wake one: a node's kill by the seed (its peers see its connections end),
a node's restart, a partition's heal (it delivers what the cut held). A partition's start
cannot: with every thread waiting and nothing else ahead, no traffic is in flight, so the cut
holds nothing and its heal leaves the links as they were. With only partition starts ahead
the run is deadlocked, as it would be without partitions; with another event ahead too, the
partitions that fall before it happen. A kill counts once faults may act: before
`setup-complete` under `faults-after-setup=1` it would only be drawn again, so it does not.

**A node's own end.** A node is up while its first process runs. When that process ends by
itself, the node's other processes are killed and the node is down: an exit status outside
the node's `ok-exit` (default `0`) ends the run `failure`, and a death by a signal Patina did
not send ends it `crash`, both naming the node (`result.json`'s `node_end`, and its stderr in
the summary). An exit within `ok-exit` only stops the node. A node's `restart` key says what
follows its downs: `crash` (the default: restarted after a seed's kill), `always` (also after
an exit within `ok-exit`) or `never`; a script's kill is never followed by a restart but the
script's own `node start`. A node's keys for this: `restart`, `ok-exit` (a status or a list),
`max-incarnations` (1 to 64, the most a node starts by the seed's kills and its restarts;
the script's `node start` goes up to 64) and `count = N`, which makes N nodes of
one table, named `NAME1` to `NAMEN`:

```toml
[node.replica]
cmd = ["python3", "/guest/q3.py"]
restart = "always"
ok-exit = [0, 3]
count = 3
```

### Crashing a node's machine

`patina ctl node kill NAME` (without `--process`) crashes node `NAME`'s machine, and
`--crash machine` has the seed do it (`--crash machine@a,b`: only those nodes), at the times it
draws for its kills, with the same `crash-gap-ms`, `down-ms`, `max-incarnations` and `restart`.
A machine crash differs from a process kill in three ways.

- **The disk.** Each node's work tree is a disk of its own. What the node had not synced may be
  lost: its next boot starts on what a file system would have kept, drawn from the seed under
  the run's `fs-model`, as for a single machine's crash ([Crashes](#crashes)); what it synced
  (`fsync`, `fdatasync`, `sync`, a synced directory) is kept, stores through a shared mapping
  included. No other node's disk is touched. `/tmp`, `/dev/shm` and System V shared memory
  start empty, as after a reboot.
- **Silence.** The node sends nothing as it goes down: no FIN, no RST. A peer learns of it only
  from its own timeouts: what it sends to the node is held, and its connection fails with
  `ETIMEDOUT` after its `TCP_USER_TIMEOUT` (or Linux's 924.6 s); a peer that only reads waits,
  unless it keeps the connection alive (`SO_KEEPALIVE`): its probes go unanswered and it fails
  with `ETIMEDOUT` after idle + count x interval, or with `ECONNRESET` if a probe reaches the
  node once it is back.
  A connect to the node while it is down retries its SYN and times out; it is not refused.
  Datagrams to it are lost. Once the node is back, it answers a segment of a connection it no
  longer has with a RST: the peer's next send resets its connection.
- **The restart.** After the down time the node's command runs again on that tree, with the
  next `PATINA_INCARNATION`; a script's crash is followed only by its own `node start`.

#### At a node's crash points

A node's crash points are its own: each node counts them on its own disk, after each record of
its operation log and before each sync, from 0 at each boot. `--crash machine-at:N@NODE`
crashes node `NODE`'s machine at the N-th point of its first boot (once); `--crash
machine:PERMILLE@NODE,...` crashes each named node at each of its points with that chance, in
every boot until its `max-incarnations`. Without `@`, every node but the driver (and a node
with `faults = false`); `N` and `PERMILLE` may be ranges (`A..B`), each node drawing its own
from a seed of its own. The
crash is the one above: the node's maps are flushed, the disk ends with its `Crash` record, the
node goes silent and boots again after `down-ms`. `--crash process-at:N@NODE` kills node
`NODE`'s processes at that point instead, as the seed's kill does (a process kill, the previous
section): its disk is kept whole, and its command starts again after `down-ms`; `downs[].how`
is `killed`, with the `point`. There are no crashes at drawn times then, so
`crash-gap-ms` is refused beside it.

After any machine crash of a node (at a point, at a drawn time or by a script), the crashed
disk's tree is written to `RUNDIR/node/NAME/inc-K/post-crash/`, the tree boot K+1 started from, and what the crash lost there is counted in `downs[].lost` and the `crash` event
(`missing`, `changed`, `back`: written and not kept, kept in another form, reverted to an older
form; `paths`). `patina log events` merges each node's operations with the driver's, each
`op` naming its `node`, and its `crash` events name the node and the `point`.
`result.json` gives each down its `point`, and each node its `crash_points` per boot.

`patina sweep --branch --crash machine[@NODE,...]` runs each seed once with crashes on and
never firing, counting every named node's points, then once per point of each node, crashing

whole run. `ack2.py` (in `tests/guests/nodes`) is a store of two nodes: a forwards each put to

### Disk faults per node

The disk and memory keys (`fs-*`, `fsync-*`, `enospc-after-bytes`, `mem-*`, `path-swap-*`)
are each node's, as are the pause and clock keys (`pause-*`, `clock-skew-ms`, which only a
node has). Given without a scope they act on every node but the driver; `@NODE,...` after
the value names the nodes (`driver` among them, if wanted); a node's `[node.NAME.faults]` table
sets its own, replacing the run's:

```sh
patina run --faults disk ...                              # every node but the driver
patina run --fault fsync-error-permille=5@a,driver ...    # a and the driver only
```

```toml
[node.b.faults]
fsync-error-permille = 5
```

Each node draws a range from a seed of its own and counts its own calls (`fs-error-at`,
`fsync-error-at`, `enospc-after-bytes`) over all its boots; `result.json` shows each node's settings as
`KEY@NODE`. The other keys are
the run's and take no scope. A node with `faults = false` in its table gets none of its own:
like the driver, it is left out of `--faults`, `--fault` and `--crash` given without a scope,

### Pausing a node

A paused node is a frozen machine, as a VM paused by its host, a process stopped by a long
garbage collection or a stalled disk would make it: none of its threads runs, but its sockets
stay open and its peers see a live machine that does not answer.

`patina ctl node pause NAME` freezes node `NAME`; `node resume NAME` lets it run again. A
pause of a node that is down or starting answers `EAGAIN`, of one already paused `EALREADY`;
a resume of a node not paused `EALREADY`; the driver cannot be paused (`EINVAL`). The seed
pauses nodes with `pause-gap-ms=A..B`, a node's own key (`@NODE` scopes it; refused without
nodes and for the driver): after a gap drawn from `A..B` the node is paused for a length drawn
from `pause-ms` (default `100..15000`), then the next gap is drawn from the pause's end.

```sh
patina run --config cluster.toml --fault pause-gap-ms=1000..8000@p1 --fault pause-ms=100..4000@p1 -- python3 driver.py
```

What a pause does:

- **Threads.** None of the node's threads is picked while it is paused, whatever it waits
  for. A thread inside a call when the pause takes effect finishes that call as at that
  instant and stops before it returns to its program; a thread holding a lock keeps it. A
  process the node forks while the pause is taking effect is frozen too.
- **Clocks.** The node's clocks are not stopped (the machine is frozen, not its clock): a
  sleep, futex timeout, timerfd or interval timer that falls due while it is paused is due at
  its time, and its thread runs at the resume, all of them in the scheduler's order. A
  program reading its monotonic clock after a resume sees the time that passed.
- **Network.** What a peer sends to the node is held, as across a cut: the peer's writes go
  on until its buffer fills, its reads wait, and a peer that has data the node has not
  acknowledged gives up after its `TCP_USER_TIMEOUT` (or Linux's 924.6 s), its next call
  failing with `ETIMEDOUT`. Data on its way to the node when the pause began is held too, with
  the rest of its delay; data the node sent before the pause arrives. A connect to or from the
  node waits for its SYN retries. A datagram to a paused node is lost. The node's own TCP
  timers run too (its clocks do): its keepalive probes go unanswered, so a pause longer than
  its keepalive budget times out its side as well, which its threads see at the resume (a
  host's VM pause would stop them). The node's traffic to itself is not affected. At the resume, every link that nothing else cuts carries what was
  held.
- **Kills and crashes.** A paused node can be killed or its machine crashed, by the script or
  the seed: the pause ends first, then the node goes down as it would.
- **What keeps a run alive.** A pause's end does (the node's threads run again); a pause's
  start does not, nor does a timer of a paused node (an interval timer fires on while it is
  paused and wakes no thread that runs). A script's pause with no resume, with every other
  thread waiting with no deadline, ends the run `liveness`, and the message names the paused node and how many of
  its threads would run.

`result.json` lists each node's `pauses` (how many), `pause` (each one's `by`, `at_ms`, `ms`,
`null` while in force at the end, and `end`: `seed`, `script`, `down` or `in force`) and
`paused_ms`; `patina log events` has `node` events `pause` and `resume`; `faults.counts.pause`
counts the seed's pauses. With `nofence`, the lease-based service of `lease.py` (in
`tests/guests/nodes`) writes as a stale primary when a replica paused after checking its
lease resumes after another took it; with fencing at the store the same sweep is clean
(`tests/nodes/17-lease.sh`).

### Each node's clock

The run has one virtual time. A node's monotonic and boot-time clocks, and every timeout,
sleep and relative timer, are that time, on every node at the same rate. A node's realtime
clock (`CLOCK_REALTIME` and what derives from it: `gettimeofday`, `time`, the times the node
writes on its files, `/proc/stat`'s `btime`) is that time plus the node's offset; the
driver's offset is always 0, so the driver's clock is the run's reference. No clock runs fast
or slow.

`clock-skew-ms=A..B` (a node's own key: `@NODE` scopes it; refused without nodes and for the
driver) gives each boot of a node an offset drawn in `A..B` ms, ahead or behind.
`patina ctl clock step NAME +90s` (or `-5s`, `+250ms`; at most a year, and `EINVAL` for one
that would put the node's clock before 1970) moves node `NAME`'s
clock, as setting the clock on a machine does; a step stays across the node's restarts, and
a node's offset is its boot's skew plus the steps so far. A step does what Linux does when the
clock is set: an absolute `CLOCK_REALTIME` deadline (`clock_nanosleep` with `TIMER_ABSTIME`,
`pthread_cond_timedwait` on a realtime condition variable, a timerfd armed with
`TFD_TIMER_ABSTIME`) moves with the clock, and one now past is due at once; a relative one, on
any clock, does not move; a realtime timerfd armed with `TFD_TIMER_ABSTIME |
TFD_TIMER_CANCEL_ON_SET` becomes readable and its next read fails with `ECANCELED`.
`adjtimex`, `clock_settime` and `settimeofday` are refused as on one machine: only the driver
moves a clock.

```sh
patina run --config cluster.toml --fault clock-skew-ms=0..2000 -- python3 driver.py
patina ctl clock step p1 -5s     # in the driver
```

`result.json` shows each node's `clock` (`offset_ms` at the end, `skew_ms` of each boot,
`steps`, `stepped_ms`); `patina log events` has `node` events `clock` (`by` `seed`, with
`skew_ms`, or `script`, with `step_ms`, and the `offset_ms` that followed); event times stay
the run's virtual time. `faults.counts.clock` counts the realtime reads of the nodes with a
skew (eligible) and those the skew moved (injected), so a sweep whose nodes never read the
realtime clock lists `clock` as not applicable. With `wallclock`, `lww.py` (a last-writer-wins
register on two nodes, in `tests/guests/nodes`) stamps each put with the node's own clock and
loses a later put when one node's clock is behind the other's; with a hybrid logical clock it
keeps every put. With `realtime`, a replica of `lease.py` that measures its lease on
`time.time()` answers stale reads after the driver steps its clock back while a partition
cuts it off from the store; on its monotonic clock it does not (`tests/nodes/17-lease.sh`).

### The cluster preset

`--faults cluster` (only in a run with nodes) is the faults a cluster meets:

| | Settings |
|---|---|
| link faults | `net`'s keys (on the links `net-links` names) |
| partitions | `partition-gap-ms=5000..60000 partition-ms=500..20000` (two nodes or more) |
| pauses | `pause-gap-ms=10000..120000 pause-ms=100..15000`, each node its own |
| clock skew | `clock-skew-ms=0..2000`, each node its own |
| machine crashes | `--crash machine` at `crash-gap-ms=30000..300000`, every node; a `--crash` given replaces it |

`--faults all` in a run with nodes is the disk, memory and network faults, partitions (two
nodes or more), pauses and clock skew: `cluster` without the machine crashes, which a run
asks for with `--crash`, as on one machine. A class the preset turned on that had nothing to
act on (no pause drawn in a short run, no realtime read on a skewed node) is `not
applicable`. `patina report` adds a line for the nodes' pauses and one for their clocks.

**Not available yet** (refused, naming what is missing): the SDK's fault keys
(`buggify-permille`, `point:LABEL`) with nodes, which would need each node's own SDK settings
in the runtime, `patina __native` twins and `--check` reference runs of a run with nodes.

## The SDK

Without the SDK, Patina finds what makes a program exit nonzero, die, hang or deadlock. The
SDK adds invariants and fault points. It is one reserved system call: outside Patina the
kernel answers `ENOSYS` and every SDK call becomes a load and a branch, so it ships in
production builds without flags.

| Call | Meaning |
|---|---|
| `always(cond, label)` | must hold; a false one ends the run `violation` |
| `unreachable(label)` | must not be reached; reaching it ends the run `violation` |
| `sometimes(cond, label)`, `reachable(label)` | should hold or be reached in some run of a sweep |
| `buggify(label)` | a fault point: true on seed-chosen evaluations under `--buggify` |
| `knob(label, default, lo, hi)` | a seed-chosen value under `--buggify` |
| `mark(label)` | a named point in the run's log, label in clear (up to 255 bytes, so it can carry data: `mark("ack 17")`); `setup_complete()` is `mark("setup-complete")` |
| `control(words)` | a control call (C: `patina_control`), such as `net cut a b` in a run with nodes ([Several machines](#several-machines)); raises (returns) the errno Patina answered |

A mark records what the program promised, where it promised it; a checker decides whether
the promise was backed. `patina log events` shows each mark's label, process and place among
the calls and file operations, so "every acknowledgement follows the fsync of its record" is a
few lines of `jq` that find the bug in every run, crash or not
(`examples/checks/synced-before-mark`, [Checks from outside the
program](#checks-from-outside-the-program)). Every SDK call's label is in the log in clear, so
a run that makes SDK calls changes its digest when a label changes.

Under `--buggify` each point is active in about a quarter of runs and fires on about a
quarter of its evaluations; `--fault point:LABEL=PERMILLE` fixes one point's rate. A sweep in
which a `sometimes` never held, a `reachable` was never hit, or (under `--buggify`) a
`buggify` point never fired is `vacuous` unless the label is allowed with `--allow-unmet
LABEL` (or `[sdk] allow-unmet` in `patina.toml`). A `buggify` point that no run evaluated
counts from 20 runs under `--buggify`, and one evaluated but never fired only when, at its
rates and evaluation counts, missing every time had a chance under 1 in 1,000; a smaller miss is
noted on one line (`sdk.buggify_unfired_noted` in `report.json`) and does not fail the sweep. A `*` in it matches any text: a library's
labels share a prefix, so `--allow-unmet 'fjall-*'` allows the sites a program does not reach
in a library it uses, and `--allow-unmet '*'` allows every label (when the oracle is a
`--check`). The summary gives a count per kind and the first five labels; `report.json` lists
all of them, with every `always` never evaluated, and the allowed ones under `allowed_unmet`. An `unreachable` that no run reached is
what it should be, and is not listed. `report.json`'s `sdk.sites` has every site with the number
of runs that evaluated it and that it held in (`runs_evaluated`, `runs_held`: a `sometimes`
true, a `reachable` hit, a point fired), so how often a sweep reached its goal is one `jq`
away. A pattern that matches no label, fault class or `check` of the runs is named on its own
line (`allow_unmet_unmatched`): an unquoted `*` that the shell expanded to file names leaves
the sweep `vacuous` otherwise without a hint.

A driver that runs one scenario of several still declares every scenario's sites (the Go SDK
declares them at package level, the others at first use or load): give each scenario's labels
a prefix of its own (`upload-*`, `resume-*`), and a sweep of one scenario allows the others'
(`--allow-unmet 'resume-*'`), as a library's are allowed below.

This stays strict on purpose: a `sometimes` you wrote that no run met fails your sweep, since a
search that never reached what it was meant to reach found nothing there. Patina cannot tell a
library's sites from the program's by itself (a static link puts them in one image, and labels
carry no owner), so a library's are allowed by its prefix, once, in `patina.toml`:

```toml
[sdk]
allow-unmet = ["fjall-*"]
```

When most unmet labels share a prefix, the `vacuous` line suggests that entry; the allowed ones
are counted on one line, `sdk: 12 sites unmet, allowed by --allow-unmet ('fjall-*' 12;
report.json: allowed_unmet)`, so they stay in view (an exact label has no count).

**Rust**: in `Cargo.toml`, the SDK at the release's tag (or `path = "PATINA/crates/patina"`
for a checkout). It needs Rust 1.85 or later (edition 2024):

```toml
patina-dst = { git = "https://github.com/JacobHayes/patina", tag = "v0.18.0" }
```

```rust
if patina_dst::buggify!("batch-commit") && !ledger.is_empty() { /* the rare path */ }
patina_dst::always!(ledger.is_sorted(), "ledger-sorted", "after {entry}");
```

The feature `compute` is for code rebuilt with compute points
([Deeper search](#deeper-search-rebuilt-code)).

**C and C++**: `cc -I PATINA/sdk/c`, one header.

```c
#include "patina.h"
PATINA_ALWAYS(acked <= stored, "acked-records-kept", detail);
```

**Go**: pure Go, no cgo: `go get github.com/JacobHayes/patina/go/patina@v0.18.0` (the
module's tags are `go/patina/vX.Y.Z`; `@main` gives the current one).
`examples/bank-go/go.mod` builds against its checkout with a `replace`.

```go

```

`go/patina/compute` is for code rebuilt with compute points
([Deeper search](#deeper-search-rebuilt-code)).

**Python**: one file, `sdk/python/patina.py`; copy it next to the program or put its
directory on `PYTHONPATH`.

```python

```

Other languages can speak the wire directly; `sdk/c/patina.h` documents it.

arguments as the program passed them: `path` and `path2` (a path, a rename's new path; for
the attribute calls the attribute's name, for `memfd_create` its name), and for each path the
call walks, the absolute path it reached, `resolved` (`resolved2`): symlinks on the way
followed as the kernel follows them, relative names taken from the working directory or the
directory descriptor, `.` and `..` gone. `execve` has `argv` (at most 256 arguments and 32 KiB;
`argv_cut` when some were left out or one was longer than 4096 bytes). A path is kept whole up
to 4096 bytes (`path_cut` beyond: the kernel refuses such a path). The strings are what the
program saw, in its own view of the file system (`/work`, `/usr`, never a host path of the
sandbox). `resolved` is the walk's result whether or not the call succeeded: select on `ret`.
A call that answered `EFAULT` has no strings, and a walk that failed (a missing directory on
the way) has no `resolved`.

The flag is off by default because the log grows: W1-W9 at seed 3 (x86_64) gained 0% (W8,
sockets), +1.3% to +1.9% (W2, tokio), +3.4% (W4, Go), +8.9% (W1, Rust), +10% (W3 SQLite, W9
fjall), +24% (W6 shell pipelines, W7 fork and exec) and +32% (W5, a CPython start and its
imports). It is part of the run: `run.json` names it, the rerun line and `replay` carry it,
and a run with it has another digest than one without; a run without it has the log it had
before the flag existed. Each recorded call costs about half a microsecond of CPU (an open in
a loop of opens: 5% to 10% more CPU); W1-W9's wall time, the least of three runs each, moved
by at most 3 ms or 4%; without the flag the cost is not measurable.

Strings from the program (`label`, `text`, `path`, `argv`, ...) are JSON strings when they are UTF-8. Otherwise
each byte that is not is U+FFFD in the string and the exact bytes are in a second field with

the program's pointer did not cover (`ret` -14, `EFAULT`) has no `label`, nor does one
whose strings a sweep's cut log or the log limit left out (a reader should allow for it).

Not in it: without `--log-paths`, the path and argument strings of calls (only their hashes,
`in`) and the process of a call (an `op`, a `fault` and an SDK call have `pid`; a `call` has its
thread's `slot`, which is not a process id),
buffer contents (read the trees: `patina log tree`, `--post-crash`). A run directory a sweep
pruned (an `ok` run without `--keep all`) has no logs: the command says so and exits 2. Types
and fields are only ever added: a reader should ignore what it does not know.

## Reading a failing run

`patina explain RUNDIR` tells a run as a short story: who sent what to whom, what reached the
disk, what the seed did (faults, partitions, crashes, node events), what the program printed
and how it ended, with each line's event number and virtual time since the run began. It ends
with the event worth stopping at. The acklog run of seed 3 above:

A record's write, its acknowledgement's write and an fsync are one disk line, 23 times: the
fsync is of `acks.log`, never of `data.log`, so at the crash every record was still unsynced.

The boundary log holds no buffer contents, only their hashes. To show what a program sent and
printed, `explain` replays the run once (into `RUNDIR/explain`) with observation on: the
runtime keeps the first 128 bytes of each read, write, send and receive in
`RUNDIR/explain/inc-K/observe.log`, beside the log and outside it, so the replay's log, digest
and outcome must equal the run's, and are checked as `patina replay` checks them. A replay that
differs ends `nondeterministic` with the first difference, and there is no story. The payload
heads stay in the run directory: delete `RUNDIR/explain` before sharing one whose program
handles secrets. A second `explain` of the run reuses that replay. Bytes are shown as text,
escaped (`\n`, `\"`, `\xNN` for the rest), at most 64 characters with `...` after.

Who: the node's name in a run with nodes (`driver` for the driver); on one machine `main` and
`t1`, `t2`, ... for the threads in the order they started, with `/pPID` after a thread of
another process than the first (`t2/p4`: a thread of process 4). With several threads on one
machine, each turn of a thread is a line: its calls, the threads and processes it started,
which threads it woke and how the turn ended (switched out by the seed, waiting for a lock, for
I/O, sleeping, ending). A message is `-> PEER "bytes"`; between processes over a pipe or a
socket pair, the peer is found when one read returns what one write sent.

What is left out and folded: calls with nothing to show, a run of disk changes of one actor
merged into one line until it repeats, a turn of only calls in which nothing started or ended
(when the story is longer than its window), and repeats: up to 12 lines that come back at
least 3 times in a row, numbers aside, are kept once with `... N times in all, until here`.
Faults, partitions, crashes and node events before the window are listed first, folded by kind.
By default the last 40 lines are shown; `--from SEQ`/`--to SEQ` (event numbers) and `--full`
(every line, nothing folded; pipe it to `grep`) choose others. `--format json` prints
one JSON object per line: the outcome, then each line (`kind`, `who`, `text`, `seq`, `t` in
virtual nanoseconds, and `to` for a message whose receiver is known), then the stop line.

The stop event: for a failed assertion, the assertion. Otherwise the actor that failed (the
node that ended the run, or the thread whose exit or signal ended it) and, before its failure's
output, the last message that reached it or the last error or fault it met; else that output.
`patina log events RUNDIR --from N --to N` prints its record. Of a run that passed the story is
told the same way, without a stop. Under `--preempt points`, a run whose threads exchanged
nothing through the log before the failure and were preempted in computation says so: a race in
the program's own memory is not in the log, and the story cannot show its cause;
`patina log events RUNDIR --types preempt,call` lists where the threads switched.

`explain` works on a run directory a sweep kept (cut logs and compressed trees included) and on
one it pruned (compared by its digest), and, like `replay`, refuses a run of another Patina
build.

explain's stop event unless `--at` names another, then starts gdb attached to the process about
to act, with a helper that gives gdb the program's symbols (Patina's runtime loads the program,
so gdb cannot find them itself). Every other thread and process is parked, as it is between
turns of any run. The acklog run of seed 3, stopped at its failed assertion:

Frames 0 to 8 are Patina's runtime: every system call of the program is a signal to it, and the
stop is inside that signal's handler; gdb starts in the program's frame under it. The event
has not happened: the assertion's call is about to be made.

`--at` takes a sequence number (as `explain` and `log events` print them) or a name for one:
`stop` (the default), `end` (the last event of a program), `crash` (the last crash),
`call:NAME[:NODE][:K]` (the K-th call of that name, of one node; K from 1, or from the end when
negative; the last when left out), `mark:LABEL[:K]`, `sdk:LABEL[:K]` and `fault:K` (the K-th
injected fault). The banner names the process and thread at the stop: the one whose turn it is,
or for the supervisor's own events (a fault, a partition, a crash) the last one to ask it
something.

What the session may do and still be the recorded run: read anything (backtraces, variables,
memory, registers), set breakpoints and watchpoints, step and continue. The world goes on when
gdb continues, detaches or quits, and the replay runs to the end. Its logs are then compared
with the run's, as `patina replay` compares them: `identical`, or `the session left the
recorded run at seq M`, where M is the first record that differs, with what the session did
that changed it (it wrote memory or a register, or called a function in the program).
Everything after M is another run, which no seed reproduces. The same verdict is in
`RUNDIR/debug/session.json` (`identical`, `left_at`, `did`), for scripts; exit status 0 when
identical, 2 otherwise.

Ctrl-C in gdb stops the process at its next request to Patina: gdb reports a `SIGTRAP` in the
runtime (`patina: interrupted (Ctrl-C)`), and continuing goes on as before. If gdb crashes or
is killed, the world goes on (a process gdb left stopped is continued) and the replay runs to
its end; a breakpoint gdb had inserted stays in the program and makes that another run, which
the end says. If `patina debug` itself is killed, the sandbox dies with it, as with any run.

In a run with several processes or nodes, gdb is attached to the one about to act. `patina
procs` in gdb lists the others with their sandbox and host pids and nodes, `patina attach PID`
(a sandbox pid) moves gdb to one of them, and `patina where` repeats the stop. The world stays
parked while gdb moves.

`--no-gdb` prints the stop and how to attach (gdb with the helper, or any debugger by host
pid), and the world goes on when Enter is pressed (without a terminal: when the file the
banner names is created) or a debugger started with the helper continues, detaches or quits.
Without gdb on `PATH` (or `PATINA_GDB`), it does the same. The helper needs gdb 12 or later.
Attaching needs a host that lets a user debug their own processes: `kernel.yama.ptrace_scope`
0 or 1 (Ubuntu's default is 1; the sandbox's processes are in a user namespace you own, so no
privilege is needed), and a container that allows `ptrace`. `patina doctor` checks it
(`debugger attach`). In this version `patina debug` does not take a run whose threads
yielded at spin points: those come of single steps and breakpoints the runtime takes with
`SIGTRAP`, as gdb does. A spin probe the supervisor sends while gdb holds the program (a thread
that ran 20 ms of CPU time without a system call) stops gdb (`patina: a spin probe ...`);
continuing drops it, which changes nothing unless the program was spinning.

A `--preempt points` or `branches` run takes `SIGTRAP` for its scheduling points too. There
reading, breakpoints, watchpoints, `finish` and continuing are as exact as in any run, but gdb
refuses stepping (`step`, `next`, `stepi` and the like are errors, and the run is unchanged):
set a breakpoint and continue instead. On arm64 `patina debug` does not take such a run in
this version. Ctrl-C does not interrupt such a run. Code the plan
moved shows as the program's own in `bt` (`patina: N trampolines mapped ...`).

The debugger is yours and can change the program as it runs: that is why a session that writes
says where it left the run. Nothing about the sandbox is different in an ordinary run: the
stop, and what the runtime does with gdb's signals, exist only in a `patina debug` replay
([ARCHITECTURE.md, "Debugging a run"](../ARCHITECTURE.md#debugging-a-run)).

## Replay and verify

`patina replay RUNDIR` runs the program again with the run's settings, into `RUNDIR/replay`,
and compares every boundary record. It refuses a program whose SHA-256 changed, and a run made
by another Patina build (another version, or another binary of one): install that version
(`install.sh --version VERSION`) or run the seed again. `identical` means the bug is
reproduced exactly (of a run a sweep pruned, which kept no logs, the digest, a hash of every
record, is compared); a difference ends `nondeterministic` and names the first differing
record, which is a Patina bug unless the host's files changed: the program is the file the
command names (a `#!` script itself), and what it runs from the host (a script's interpreter,
shared libraries, anything under `/usr`) is not recorded. A run notes what each `--mount`
source held (its entries' names, types, modes, sizes and modification times; up to 20000
entries); a difference after one of them changed ends `error`, stop `inputs-changed`, naming
the mount: the program read other inputs. Of a host file's metadata the program sees its type,
mode, size and modification time (and inode number): its other times read as the modification
time and its link count as 1, so a hard link made elsewhere or a `chmod` changes nothing it sees.

A replay refuses a rebuilt program; to check a fix, run the finding's `rerun:` line instead.
It names the program by path and carries the seed, the faults, the checker and the case (with
`--config RUNDIR/run.json` for a case run), so against the rebuilt program it runs the same
test: the finding gone (`ok`, or the checker's `pass`) is the fix verified for that seed.
The same sweep command then checks every seed again (a rebuilt program starts the sweep
afresh).

`patina verify` runs one seed several times while changing the host (the CPU it runs on,
address randomization, background load) and checks the runs are identical:

`--vary` also takes `sandbox` (host counters moved between runs), `parallel` (runs at once),
`env` and `time`. `time` waits before the second run, so a host clock that leaks into the
run reads differently there; the host's clock cannot be moved without privilege, so the wait
is the variation. It waits `PATINA_TIME_GAP_S` seconds, 61 by default
(past a minute boundary: a leak at second or minute resolution shows).

## Scheduling

One thread of the program runs at a time; the seed picks the next one at each scheduling
point. The points are every system call, every spin hint (`pause`; on arm64 `yield`, `isb`,
`wfe`, `wfi`),
and spin-waits Patina detects: a thread that computes for 20 ms without a system call is
stepped until it is found looping without changing anything, and yields there.

A thread that computes for 10 s of CPU time without reaching a scheduling point, while
another thread is waiting to run, ends the run `unsupported` with stop `compute-stall`. The
message names the function the thread was last seen in, and the file and offset, as a spin
probe found it (`last seen in waiter (/guest/spinpoints+0x1392)`). The
cause is a spin-wait whose loop changes state on each pass (a counter, a timestamp) and has
no system call or `pause`, or a long computation: a calibration loop that times itself
against the clock sees almost no time pass while it computes (stock code moves the clock by
a fixed charge per system call, not with computation), so it keeps raising its work. Rebuilt code, and Python under `python3 -m patina`, does not stall
that way ([Deeper search](#deeper-search-rebuilt-code)), nor does stock code under
`--preempt points` ([Points in stock code](#points-in-stock-code---preempt-points)), except in
code it leaves dark. `--preempt branches` also preempts after a
seed-chosen number of branches; it needs an AMD Zen 5 or Arm Neoverse N2 CPU with its PMU exposed (not in most virtual machines;
GitHub's `ubuntu-24.04-arm` runners expose theirs) and
`CAP_PERFMON` (`sudo setcap cap_perfmon+ep $(command -v patina)`), and its seeds reproduce
only on that CPU family. `patina doctor` says which of the three is missing.

Its stops are exact: a run stops at the branch counting every branch by hand would, with the
same registers, or it fails closed. The counter's overflow interrupt is aimed 1024 branches
(`[sched] pmu-margin`) ahead of the stop and the rest is counted by hand; on a virtual
machine the interrupt can come later than that (up to about 700 branches after the overflow
on the x86_64 one measured, 1,900 on GitHub's arm64 runners), and the run then ends
`internal`, stop `pmu-late`,
rather than stop past its branch: raise `pmu-margin` (each stop then counts more branches by
hand). The kernel's throttling of a counter that interrupts too often, which a loaded virtual
machine makes more likely, does not change where a run stops.

## Deeper search: rebuilt code

A stock program switches threads only where it makes a system call or spins. Rebuilt with a
compiler's coverage flags and Patina's hook file, its own code gets points too:

- Threads switch inside computation, so a race on plain memory with no system call in it (a
  count updated without its lock, a check and an act on an atomic) can be found.
- Virtual time advances with computation, 1 ns per event, so a timer, a timeout or
  `--time-limit` cuts a CPU-bound loop at the event where it falls due.
- A spin-wait in rebuilt code yields by itself instead of ending `compute-stall` (in Go, if
  its loop makes a comparison).

An event is one hook call: each edge (a branch taken) and, with clang and Rust, each load and
store; in Go, each comparison. `examples/stats-c` has four workers that update shared
statistics without their lock. The stock build never shows it; the rebuilt one does:

### Building

Add the flags to every compile of the code to search, and the hook file once to each
executable or shared library built with them. `PATINA` is a checkout of this repository.

C and C++ with clang (edges, loads and stores):

```sh
clang -O2 -fsanitize-coverage=trace-pc,trace-loads,trace-stores -fno-sanitize-link-runtime \
  -o app app.c PATINA/sdk/c/patina_compute.c
clang++ -O2 -fsanitize-coverage=trace-pc,trace-loads,trace-stores -fno-sanitize-link-runtime \
  -o app app.cc -x c PATINA/sdk/c/patina_compute.c
```

gcc and g++ take `-fsanitize-coverage=trace-pc` and the same file, and give edges only: a
switch lands only at a branch, so it cannot split an `x++` or `stats.done = done + 1`. The
gcc build of `stats-c` found nothing in 20 seeds, at the default gap and at 2. Prefer clang.
With gcc 11 or older, build the hook file in a step of its own without the flag
(`gcc -O2 -c patina_compute.c`) and link the object.

Rust, stable: the SDK with the feature `compute`, and the flags with `--target`:

```toml
patina-dst = { git = "https://github.com/JacobHayes/patina", tag = "v0.18.0", features = ["compute"] }
```

```sh
RUSTFLAGS="-Cpasses=sancov-module -Cllvm-args=-sanitizer-coverage-level=3 \
  -Cllvm-args=-sanitizer-coverage-trace-pc -Cllvm-args=-sanitizer-coverage-trace-loads \
  -Cllvm-args=-sanitizer-coverage-trace-stores" \
  cargo build --release --target x86_64-unknown-linux-gnu
```

The binary is under `target/x86_64-unknown-linux-gnu/release/`; on arm64 the target is
`aarch64-unknown-linux-gnu`, and the rest is the same. `--target` keeps the flags
off build scripts and proc macros, which do not link the SDK and would fail with undefined
`__sanitizer_cov_trace_pc`. A program that uses nothing else from the SDK fails the same way
unless it says `use patina_dst as _;`. Your crates and their dependencies get the hooks, with
what they inline from the standard library; the prebuilt standard library does not. A `dev`
build makes about 14 times the events of a release build for the same work, and so that much
more virtual time and switching.

Go: one blank import in package `main` and one flag, without cgo. Points are at integer and
string comparisons, in every package but the Go runtime.

```go
import _ "github.com/JacobHayes/patina/go/patina/compute"
```

```sh
go get github.com/JacobHayes/patina/go/patina@v0.18.0
CGO_ENABLED=0 go build -gcflags=all=-d=libfuzzer -o app .
```

With the flag and without the import, the link fails with `reference to undefined builtin
"runtime.libfuzzerTraceCmp8"`. `go test` binaries cannot be built this way (the testing
package defines the same hooks): build the scenario as a `main` package.

Shared libraries: each instrumented library links its own copy of the hook file, and a stock
program may load it.

```sh
clang -O2 -fPIC -shared -fsanitize-coverage=trace-pc,trace-loads,trace-stores \
  -fno-sanitize-link-runtime -o libwork.so work.c PATINA/sdk/c/patina_compute.c
```

Python needs no rebuild: see [Python](#python) below.

### Python

Python 3.12 or later runs with compute points under the SDK file's runner, with no change to
the program: put `sdk/python` on `PYTHONPATH` and start the program with `-m patina` before
the script (or before `-m MODULE`):

```sh
patina run --mount PATINA/sdk/python:/sdk --env PYTHONPATH=/sdk -- python3 -m patina app.py ARGS
```

worth 15 events, so 15 ns of virtual time, a fixed constant near what a plain line takes
natively. Threads switch between any two lines: ctypes releases the GIL at the point, so the
thread switched to runs. `tests/guests/compute/py/pycompute.py cache` fills a cache from two
threads with a check and an act and no system call between them:

CPU-bound Python now moves the clock: a timer or a `threading.Timer` cuts a loop with no
system call where it falls due, and two CPU-bound threads take
turns (stock, the one holding the GIL runs to its end, or to `compute-stall` after 10 s).
Outside Patina (or under a Patina before this feature) the runner makes one failed call and runs
the program as `python3 app.py` would, with nothing registered and no `compute points:` line.

The cost is the interpreter calling the hook, 50 to 100 ns per line or jump. Under Patina a
tight loop ran 4 times as long as stock, a mixed pure-Python workload 1.5 times, and
`tests/guests/cpython/w5.py local` (threads, files, sqlite) 1.1 times; natively the hook would
make such code 7 to 17 times slower, which is why it is off outside Patina
(docs/EVIDENCE.md, "Python").

Limits:

- The points are at line starts and jumps of Python code. Inside one line only CPython's own
  5 ms switch request switches threads, so a race within a line (`d[k] = d.get(k, 0) + 1`) is
  rarely found, and a bytecode-atomic operation (`dict.setdefault`, `list.append`) never. C
  extensions and the interpreter's own C code have no points.
- Processes the program starts run without points unless started the same way.
- At `compute-gap=0` a line costs real time enough that a stretch between two yields (2^22
  events) can pass the spin probe's 20 ms, and the probes slow the run: 2 to 3 times on
  Python 3.12.
- The free-threaded build works the same on 3.14t (the only one tried): the race above was
  found in 21 of 40 seeds.

### The gap

`--fault compute-gap` is the one setting. Each seed draws a mean gap G, log-uniformly from
`64..65536` by default, and each stretch between two switches is uniform in `1..2G-1`
events. The draw depends on the seed alone: seed 2 draws 248 in every program.

| Setting | For |
|---|---|
| `64..65536` (default) | long programs: the measured ones ran 1.2 to 2 times as long as stock, and their races that recur were found |
| `2..64` | short programs, tests whose threads run tens of events: found such races 13 to 43 times as often as the default |
| `0` | no switches; time and deadlines still apply |

A single number (`compute-gap=8`) gives every seed that G.

Each switch writes one 96-byte record to the boundary log, so a long program at a small gap
can reach `--log-limit` (default 1 GiB, about 11 million switches) and end `liveness`, stop
`log-limit`: raise the limit or the gap.

### Limits

- A seed found on a stock build does not replay on a rebuilt one, or the reverse: they are
  different binaries. Each repeats on its own.
- Code not rebuilt (libc, the prebuilt Rust standard library, the Go runtime, any prebuilt
  library) has no points and costs no virtual time. A race wholly inside it stays out of
  reach.
- One thread runs at a time, so weak-memory behaviours (a store another CPU sees late) never
  happen, and a `lock`-prefixed read-modify-write is never split.
- With `--preempt branches` the hooks do nothing (Python's is not registered); branch
  counters switch instead.

## Points in stock code: `--preempt points`

`--preempt points` gives a stock program compute points without a rebuild: as the
program and each library it loads are mapped, Patina maps in a rewritten copy of their text
with a count before every backward branch, backward call, indirect jump and atomic instruction
it can patch. The counts are compute-point events: threads switch there at a seed-chosen
event, virtual time advances 1 ns per event, and a timer or `--time-limit` cuts a CPU-bound
loop where it falls due. Nothing about the program changes on disk.

The check-then-act race of `tests/guests/compute/go/race` (two goroutines read a balance with
an atomic load, then withdraw with an atomic add; no system call between), built stock, ends
`ok` on all 20 seeds without points. With them, at the small gaps short programs need
([The gap](#the-gap)):

`patina run` prints a `load-time points:` line: the points taken, each rewritten file with the
share of its sites patched and of its text left dark, and anything left without points.
`result.json`'s `rewrite` has the counts (`points`, `stays`, `applied`, `dropped`, `restored`,
`unplanned`, `cpuid`, `interior`; the walks' counts, below) and one entry per file the program
mapped executable (`images`: `path`, `sha256`, `status`, and for a planned file `sites`,
`patches`, `covered_pct`, `back_edges_covered_pct`, `dark_pct`, `cpuid_patched`,
`cpuid_unpatched`, `cache`: `hit`, `made`, `rebuilt` or `bypassed`, and `rewrite_ms`).

**Walks.** A window between two plain memory accesses with no branch, call or atomic between
them (a counter loaded, changed and stored) holds no point. So under `--preempt points` a
switch is sometimes taken a few instructions past its point: 2 switches in W are taken a drawn
1 to W instructions on, the program single-stepped there, the rest at the point. W is drawn
per seed, log-uniformly from 4 to 512 by default (`--fault compute-walk=W` or `A..B`; `0`
takes every switch at its point). A walk ends, and its switch is not taken, where the
program enters Patina (a system call, a fault, a spin hint); it never stops inside Patina's
copied code, and switches before an x86_64 `pushf` or an arm64 exclusive load. The run's
`load-time points:` line counts the switches taken after a walk (`result.json`: `walks`,
`walk_steps`, `walks_cut`, and `walk_max`, the seed's W). A walk costs about one single-step
per switch, whatever W is. On arm64 walks write breakpoints through `/proc/self/mem`; a host
that refuses that ends the run `internal` (or set `compute-walk=0`).

The lost update of `tests/guests/rewrite/races.c lms` (a load and a store through a pointer, in
a loop) is found on about 1 in 10 seeds at the default gap with walks and on none without, and
on half of them at `compute-gap=2..64`. One further from a point is found rarely:
`examples/stats-c`'s lost update on 1 or 2 of 200 seeds. Rebuilt code puts a point at every
load and store.

**What it costs.** A point the program takes is a trap into Patina, and a switch there a
hand-over through the supervisor (tens of microseconds with its walk, on the measured hosts). So
Patina takes only the points that can switch: a thread with no other thread runnable counts to
its next deadline without stopping, and where the seed's draw would keep the running thread at a
point, the count runs on to the first point whose draw switches (the points passed are `stays`
in `result.json`'s `rewrite`). Each decision is still drawn from the seed for the point it falls
on; only the trap is skipped. With the gap drawn by default, a run takes about 32768 switches at
its gap and then one per 8192 events: past that, its gaps are drawn with a mean of at least 8192
until it is back within. That keeps a long program at a small gap within about 3 times its run
without points (docs/EVIDENCE.md); a test of a race never reaches it. A gap the plan names
(`compute-gap`) is used for the whole run.

**What each reaches, and when to use it.**

| Mechanism | Threads switch | Reaches | Use it |
|---|---|---|---|
| System calls (always) | at every system call | races between calls: locks, files, sockets, channels | always on |
| Spin hints and probes (always) | at `pause` (arm64 `yield`, `isb`, `wfe`, `wfi`), and in a loop found spinning after 20 ms of CPU | spin-waits hand over instead of stalling | always on |
| `--preempt points` | before backward branches, backward calls, indirect jumps and atomics in every file the program maps | a window with one of those in it: check-then-act on atomics, loops, retries | stock programs and libraries you cannot rebuild, on any x86_64 or arm64 host |
| Walks (with `--preempt points`) | 1 to W instructions past such a point | straight-line windows near a point: a load, a change and a store | on with points; raise W, or lower the gap, for a window further from a point |
| `--preempt branches` | after a seed-chosen number of branches | every branch, in every file | on an AMD Zen 5 or Arm Neoverse N2 PMU with `CAP_PERFMON`; seeds repeat only on that CPU family |
| Rebuilt code (compute points) | at every edge, load and store (Go: comparison) | every window in the rebuilt code, between any two accesses | code you can rebuild: the densest, and its seeds repeat on any host |
| Python under `python3 -m patina` | between any two lines | races between Python lines | Python programs |

**The plans.** A plan is made on the host from a file's bytes and the Patina build alone, so
it is the same on every host; each is checked by an independent verifier before it is used,
and kept in `~/.cache/patina/plans/` (`$XDG_CACHE_HOME`; at most 4 GiB, the least recently used
removed first; deleting it costs only time). Patina plans the program and the libraries it
names before the run starts, and any other file (a `dlopen`, an `execve`) when it is mapped.
The first run pays for making them, on up to 8 threads (the plan is the same bytes on any
number): 0.2 s for ripgrep, 0.4 s for CPython and its libraries, 3 s for clang, 5 s for
headless Chromium (49 files); later runs read them (docs/EVIDENCE.md). A sweep makes them once,
before its runs start, and runs or sweeps that meet one file at once make it once between
them. A run waits for another process's plan of a file at most 5 s and a second per 2 MiB of
the file: past that, stderr names the process and its lock file, and the run makes the plan
itself without keeping it (`bypassed`; the same plan, so the same digest). When planning takes
longer than a second, one line on stderr says so:

<!-- no-run planning-notice: printed while a cold run plans headless Chromium; the directory is the host's -->
```text
patina: --preempt points: planning chrome-headless-shell and 45 more files, once: plans are kept in ~/.cache/patina/plans
```

`patina cache` prints where the plans are, how many and how large; `patina cache clear`
deletes them.

**What is not covered.**
- On x86_64, about 1 to 3% of sites in typical code (as many loop back-edges) have no patch
  that fits: a count must go where the flags are dead, in place of one instruction of 5 bytes
  or more or of a short run of straight-line instructions that no known branch enters. On
  arm64 every site is one 4-byte word and the count writes no flags; a site is left only
  inside an exclusive pair (a load-exclusive up to its store-exclusive, where a count would
  make the store fail every time), on the way from a failed store-exclusive back to its load (a
  store-exclusive can fail with no other writer, and the loop goes round once more by run), at
  a word whose address code takes (it may read it), or out of a branch's reach of its
  trampoline (128 MiB) where no `x16` route fits.
  Text that no control flow or unwind entry reaches is *dark* and never patched (22% of
  Chromium's: code reached only through tables).
- Code made at run time (JIT output, memory made executable after it was mapped) gets no
  points (counted `unplanned`). A program that writes, moves, unmaps or reprotects part of its
  own text gets the original pages back there and no points in them (counted `restored`, or
  `dropped` when none of the file's rewritten pages is left); the rest of the file keeps its
  points, and mapping the file there again brings them back.

**What the program sees.** Faults, signal frames, records and unwinding name the original
addresses, never a rewritten copy's. `/proc/self/maps` shows the original files; each library
is followed by a gap where its copy's extra code lives, so libraries load at other addresses
than without points. A program that reads its own code reads the rewritten bytes (a checksum
of its text differs from native). On x86_64, a jump into the middle of a rewritten run of
instructions from code Patina could not follow (a jump table, a computed goto) traps and goes
on at that instruction, as unpatched (counted `interior`; no point, no virtual time); arm64
rewrites single words only, so there is no such middle. `cpuid` in planned
code answers the fields that name a core (APIC, node and compute-unit ids) as core 0's, so a
run does not depend on the core it was given; a `cpuid` in dark or JIT code is the CPU's.

The profile attaches to one path (`patina doctor --print-apparmor-profile` prints it for the
executable that runs it). It admits whatever file is at that path, so install patina where only
root can write, such as `/usr/local/bin` (`install.sh --prefix /usr/local`, run as root) or the
package's `/usr/bin`, rather than under your home directory.

Where `spin probes` is off, programs still run; a spin-wait with no hint instruction in its loop
ends `compute-stall`, and the stall's message says why the probe was off.

Seeds and digests are per architecture and per kind of host. A seed found on x86_64 is a
different run on arm64. On one host a seed repeats exactly. Across hosts of one architecture, a
static program that reads no host file gives the same digest, apart from what it reads of the
host: the kernel release (`uname`), addresses that follow the CPU's state size (XSAVE on
x86_64), signal-frame records that follow the CPU's features, and code a library chooses by CPU
feature when that code makes different system calls. Registers a call does not read are not
recorded, so a library routine that only leaves different values in them changes nothing. A
dynamic program reads the host's loader, libc and `/etc/ld.so.cache`, so its digest follows the
image ([EVIDENCE](EVIDENCE.md#second-hosts)).

What differs on arm64:

- The spin hints that are scheduling points are `yield`, `isb`, `wfe` and `wfi` (x86_64:
  `pause`); `RNDR` and `RNDRRS` answer from the seed (x86_64: `rdrand`, `rdseed`).
- `--preempt branches` works on the Arm Neoverse N2 only, and counts every branch, not only
  conditional ones (the same N stops sooner in the program than on x86_64). An image's first
  trap (a system call, usually) comes before its first preemption. With it, the exclusive load/store
  instructions are emulated (`patched_sites.exclusive` in `result.json`).
- Rust compute points build with `--target aarch64-unknown-linux-gnu`.
- `--preempt points` saves two registers 32 to 16 bytes below the stack pointer at each count
  (arm64 has no flags-free memory decrement); a program that keeps data there, which a signal
  frame would overwrite natively too, can see it change, and a hand-written loop that runs
  with the stack pointer not 16-byte aligned gets `SIGBUS` at a count. Sites inside an
  exclusive pair are left unpatched.
- The system call table is the generic one: no `select`, `pause`, `alarm`, `fork` or
  `epoll_create`; libc uses `pselect6`, `clone` and `epoll_create1` instead.

### As root, and in a container

Run as root, Patina gives the sandbox's user the uid of the user sudo was run by (else
`nobody`): the guest sees what it sees run as that user, with the same digest. A program or
mount the sandbox's user cannot read is refused before the run, naming the path.

A container's default profile blocks the namespaces Patina makes, as root or not. In Docker
(debian:12), `patina doctor` there says:

<!-- no-run doctor-container: needs Docker and root -->
```text
FAIL  user namespaces                    running as root, the sandbox's user namespace cannot be made (unshare: Operation not permitted (os error 1))
                                         fix: in a container: run it with --security-opt seccomp=unconfined --security-opt apparmor=unconfined --security-opt systempaths=unconfined
FAIL  personality                        errno 1 (Operation not permitted (os error 1))
                                         fix: the process runs under a restrictive seccomp profile: in Docker, --security-opt seccomp=unconfined
```

With those three options, root and an ordinary user in the container both pass `patina doctor`
and get the same digest; `seccomp=unconfined` alone still fails at the sandbox's mounts.

On a host running Ubuntu 24.04 or later, the host's AppArmor restriction applies inside the
container too: root in the container passes with the three options, an ordinary user does not.
For an ordinary user, fix it on the host:
install the profile there for the path patina has inside the container (`patina doctor
--print-apparmor-profile` in the container prints it; copy it to the host's
`/etc/apparmor.d/patina` and load it with `sudo apparmor_parser -r /etc/apparmor.d/patina`), or
set the host's `kernel.apparmor_restrict_unprivileged_userns=0`. `patina doctor` in the
container names both.
